    Objective

    Make the API and UI run against Okta, Entra ID or Auth0 as readily as against Keycloak, by making the three provider assumptions in the code and chart configurable and by documenting the identity-provider contract with a recipe per provider. Ships as v2.0.0-rc.17, before the GA cutover (DESIGN-0038 OQ1).

    Implements: DESIGN-0038 Part B (B1–B6), decisions D4–D7, OQ4–OQ9.

    Scope

    In Scope

    • OIDC_CLIENT_CLAIM on the api role (default azp), read where Claims.Client is set; the typed AZP field goes.
    • OIDC_TOKEN_AUTH_METHOD (client_secret_post default, client_secret_basic) and OIDC_AUTHORIZATION_PARAMS (JSON object, reserved keys refused) on the BFF.
    • Chart: api.auth.clientClaim, ui.oidc.tokenAuthMethod, ui.oidc.authorizationParams; nameClaim/groupsClaim in the schema; ui.oidc.scopes default aligned with the BFF's.
    • Test fixtures: Okta-, Entra- and namespaced-claim-shaped tokens in oidctest; the mock issuer accepting client_secret_basic; one e2e project on the basic method.
    • docs/operations/identity-provider.md: the contract table, the Keycloak section moved from docs/usage/api.md, Okta, Entra ID and Auth0 recipes, the Google note, verification through /me.
    • The rc.17 release bump, tag and publish.

    Out of Scope

    • Nested group-claim paths (OQ9 decided no).
    • Any change to the authorization model, /me, or the OpenAPI document.
    • ID-token acceptance at the API, opaque-token introspection, Google without a broker.
    • Homelab Keycloak reconfiguration: the defaults keep today's behaviour, so the rc.17 upgrade needs no IdP change.

    Pre-implementation audit

    Verified against the tree on 2026-10-25 (DESIGN-0038 § How the API and UI authenticate today):

    • internal/api/authn.go: AuthnConfig{Issuer, Audience, NameClaim, GroupsClaim, Now}; tokenClaims.AZP is the only source of Claims.Client; verify already reads name and groups by configured key from the full claim map, so the client claim follows the same path. isIDToken names Keycloak in its comment.
    • internal/config/api.go reads OIDC_NAME_CLAIM and OIDC_GROUPS_CLAIM with defaults; cmd/repo-guardian/api.go builds AuthnConfig from them.
    • internal/api/oidctest/oidctest.go Token has Client (→ azp), Groups, Name (→ preferred_username), IDToken, Rogue, HMAC; the header typ is at+jwt. NameClaim: "preferred_username", GroupsClaim: "groups" is hard-coded in api_test.go, status_http_test.go and apiendpoints_integration_test.go.
    • ui/server/oidc.ts passes client.ClientSecretPost; ui/server/auth.ts builds the authorize URL from six fixed parameters; ui/server/config.ts has defaultScopes = "openid profile email offline_access" and no audience or method setting.
    • ui/server/testing/mock-issuer.ts checks the client secret from the POST body only; ui/e2e/stack.ts starts two BFFs (startUI).
    • Chart: values.yaml api.auth.{issuer,audience,nameClaim,groupsClaim} and ui.oidc.{clientId,scopes: [openid, profile, groups, offline_access]}; values.schema.json declares only enabled, issuer, audience under api.auth; _helpers.tpl renders the OIDC_* env; validateUI holds the UI render guards; tests/ui_test.yaml asserts the scopes default string.
    • Docs: docs/usage/api.md § Keycloak example; docs/usage/ui.md links it; ui/README.md has the env table.

    How the phases are ordered

    API first (Phase 1) because its fixtures are what Phases 2–4 are tested against; the BFF (Phase 2) next because the chart (Phase 3) renders its new env; docs (Phase 4) once every knob has its final name; the rc (Phase 5) last. Phases 1–4 are one pull request against v2 ([[feedback-one-pr-per-impl]] in memory); Phase 5 is the release-bump pull request.

    Implementation Phases

    Each phase builds on the previous one. A phase is complete when all its tasks are checked off and its success criteria are met.

    Open Questions

    OQ1. How oidctest grows provider shapes.

    • (a) ✅ recommended: a Token.Claims map[string]any merged last plus three named constructors (Okta, Entra, Namespaced); one mechanism covers the next provider without a new field, and the constructors keep the tests readable.
    • (b) one boolean per shape (Okta bool, Entra bool); mirrors IDToken/Rogue, but every new claim variation is a new field.
    • other:

    Decision (2026-10-25): (a).

    OQ2. How the mock issuer exercises client_secret_basic.

    • (a) ✅ recommended: accept both methods always and record which one was used; the e2e no-remediation BFF runs on basic, the chromium one on post, and a unit test asserts the recorded method. No flag to thread through the stack.
    • (b) a tokenAuth: "post" | "basic" option on the issuer that refuses the other; stricter, but the stack then needs two issuers or a third BFF to cover both.
    • other:

    Decision (2026-10-25): (a).

    OQ3. Where reserved authorization parameters are refused.

    • (a) ✅ recommended: in all three places: BFF config validation (the runtime truth), validateUI (the message operators see at render) and the schema (not/required per key, so helm lint catches it too).
    • (b) BFF and validateUI only; the schema stays simpler and the render still fails.
    • other:

    Decision (2026-10-25): (a).

    OQ4. The OIDC_AUTHORIZATION_PARAMS wire format.

    • (a) ✅ recommended: a JSON object, rendered by the chart with toJson; unambiguous for values containing = or , (Entra's domain_hint values, Auth0 audiences with /).
    • (b) key=value,key=value; shorter to type by hand, ambiguous for the values above.
    • other:

    Decision (2026-10-25): (a).

    OQ5. What else rides in rc.17.

    • (a) ✅ recommended: only this IMPL; the rc exists to put the identity knobs in operators' hands before the GA docs name them.
    • (b) also the internal/controls/file/file.go quadratic duplicate-key FIX:; a real cost but unrelated, and IMPL-0034 Phase 9 carries it.
    • other:

    Decision (2026-10-25): (a).
