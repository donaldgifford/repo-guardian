# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

repo-guardian is a GitHub App (Go) that automates repository onboarding and compliance across a GitHub organization. It detects missing configuration files (CODEOWNERS, Dependabot, Renovate) and creates PRs with sensible defaults. Deployment targets: Talos k8s cluster (dev/test) and EKS (production). Documentation is managed via docz — see `docs/rfc/`, `docs/design/`, `docs/impl/`, `docs/investigation/` for structured docs.

**Core flow:** GitHub webhook OR weekly scheduler OR push event → work queue (buffered channel) → checker engine → GitHub API (create PRs for missing files) → reconcilers (post-check actions like custom property sync).

**Key design patterns:**

- **HCL policy engine** — optional `guardian.hcl` config (set via `GUARDIAN_CONFIG` env var) defines file rules with four check modes: `exists`, `contains` (with regex/YAML path assertions), `exact` (YAML semantic or byte comparison), and `absent` (forbidden-file deletion, IMPL-0019). File rules may also carry a `when { rule_satisfied = "<sibling>" }` gate. Also supports `rule "setting"` blocks (8 repo properties with optional remediation) and `rule "branch_protection"` blocks (rulesets API). Global and per-rule `ignore {}` blocks with glob pattern matching skip repos. Config merge order: built-in defaults → HCL file → env var overrides. Uses `hclparse.NewParser()` (not `hclsimple` due to `hcl:"-"` tag incompatibility). The engine has a single constructor `NewEngine(cfg, templates, logger, registry)` that builds a policy-driven `*Engine`; `CheckRepo` dispatches directly to `checkRepoWithPolicy` (post-IMPL-0014 Phase 1).
- **PR templates (DESIGN-0013, IMPL-0012 Phase 4-5)** — operators may declare `pr { title body labels inherits }` blocks at three scopes: `defaults { pr {} }`, `rule "file" "..." { pr {} }`, and `reconcile "..." { pr {} }`. Title/Body strings are compiled into `*template.Compiled` at policy-load time by `internal/policy/pr.go.compilePolicyTemplates`; parse errors fail load with a location-prefixed message. Resolution: `ResolveRulePR(rule, defaults)` and `ResolveReconcilerPR(reconciler, defaults)` perform field-by-field merge; child wins on every explicitly-set field, unset fields inherit from parent only when `inherits=true`. `inherits=false` short-circuits parent inheritance. `labels = []` is an explicit empty-list override (tracked via sidecar `LabelsSet bool` because HCL `[]string` decode loses the absent-vs-empty-list distinction). Reconciler PRs deliberately skip `rule.pr` — they merge `reconciler.pr → defaults.pr` only. Engine integration (`internal/checker/pr.go`): single-rule PRs resolve via the rule's PR template; multi-rule bundles render every rule's title and fall back to `defaults.pr.title` (or `PRTitle` const) on conflict with an `slog.Info` enumerating the ignored titles. Bodies for multi-rule bundles always use `defaults.pr.body` only (per-rule `pr.body` is implicitly single-rule, Open Q5). Bodies > 65000 chars are truncated and a marker is appended (`<!-- truncated by repo-guardian: original length=N chars, max=65535 -->`) with an `slog.Warn`. Labels are applied to PRs via the new `Client.AddLabelsToPR` API method. Reconcilers consume the pre-resolved template via `ReconcileParams.PRTemplate`.
- **Strict template validation (IMPL-0012 Phase 5.5)** — `--strict-templates` CLI flag on `cmd/repo-guardian` and `STRICT_TEMPLATES` env var enable post-load validation via `policy.ValidatePRTemplates`. Walks every compiled PR template (defaults, per-rule, per-reconciler) and runs `tmpl.ValidateZero[tmpl.PRVars]`. Failures aggregate into a single error with location prefixes; startup fails non-zero. CLI flag default is the env var, so the flag wins on the command line for one-off CI runs. Strict mode validates PR templates only (PRVars context); file-content templates in TemplateStore are not validated because legitimate Catalog references would false-positive against zero `FileVars`.
- **FileRuleConfig (policy package)** — each rule declared in HCL (or `BuiltinDefaults()`) defines paths to check, the default template name, check mode, optional assertions, scope/ignore, and attached reconcilers. New rules are added by extending the policy schema, not by touching engine code.
- **Deterministic branch naming** — single branch per repo (`repo-guardian/add-missing-files`) for idempotent PR creation.
- **Work queue** with configurable concurrency (buffered channel + N worker goroutines) for rate-limit-safe GitHub API usage.
- **Installation-scoped clients** — each job creates a GitHub client scoped to the specific installation, with cached transport tokens.
- **Reconciler pattern** — pluggable post-check behaviors attached to file rules via `reconcile` blocks in HCL config. Four built-in reconcilers: `custom_properties` (Backstage catalog-info.yaml → GitHub custom properties, `api` or `github-action` mode; Owner/Component always sync, additional annotations opt in via `annotation_properties` map — DESIGN-0019, IMPL-0017), `label_sync` (YAML-driven label create/update/rename/delete with `delete_extra` option), `branch_protection` (YAML-driven ruleset management via rulesets API), `workflow_sync` (lightweight observability for watched workflow files). Reconcilers run after file existence/assertion checks pass. Factory registry in `internal/reconciler/`. Backward compat: `CUSTOM_PROPERTIES_MODE` env var injects a `catalog_info` rule with reconciler into built-in defaults when no HCL config is present.
- **Push event handler** — webhook handler accepts watched file paths (extracted from reconcilers with `watch = true`). Pushes to the default branch that add or modify watched files trigger a re-check via `TriggerPush`. Tag pushes and removed-only changes are ignored.
- **Operator-owned ingress (IMPL-0024, DESIGN-0023)** — the app ships no ingress and reads no client-IP headers. HMAC signature validation is the sole app-layer defense (401); source-IP enforcement lives at the operator's edge per `docs/operations/ingress.md`. The former IP-allowlist middleware and baked Tailscale sidecar are gone: `webhook_rejected_total` now has exactly one producer, the HMAC 401 path (`reason="signature"`); the removed env vars (`WEBHOOK_IP_ALLOWLIST`, `WEBHOOK_IP_ALLOWLIST_FAIL_OPEN`, `TRUST_PROXY_HEADERS`) are warn-and-ignored at startup while the removed `guardian {}` HCL attrs fail load (strict decode) and the removed chart values (`tailscale.*`, `webhookIPAllowlist.*`) fail render (schema `const` + `validateRemovedValues`, both naming the migration URL). Do not reintroduce an in-app IP check — INV-0016 Observation 5: leftmost `X-Forwarded-For` is client-controlled, so it was spoofable behind every documented proxy.
- **Per-org rule scoping (DESIGN-0010)** — optional top-level `scope { orgs = [...] }` block engages strict mode where every rule must declare its own `scope { }` sub-block. Absence preserves legacy mode (every rule applies to every repo). Rule-level `["*"]` is the universal "applies to every in-scope org" idiom. Per-rule scope without top-level scope emits a single `slog.Warn` at load time. Two evaluation gates in `engine_policy.go.checkRepoWithPolicy`: policy-level (skips entire repo, increments `OutOfScopeTotal{level=policy}` once per enabled rule) and rule-level (skips that rule, increments `OutOfScopeTotal{level=rule}`). Helpers and `OutOfScopeTotal` counter live in `internal/checker/scope.go`.
- **Per-org metrics labels** — all per-rule and per-repo Prometheus counters carry an `org` label (`repos_checked_total[trigger, org]`, `files_missing_total[rule_name, org]`, `prs_created_total[org]` (CounterVec), etc.). Pre-existing scalar query semantics are preserved with `sum(...)`. Catalog and migration recipes in `contrib/README.md`.

## Testing

- Use standard Go testing with race detector enabled.
- **Mocks: generated base, hand-written fakes (post-IMPL-0021 Phase 7).** `mockery v3` (pinned in `mise.toml`, config in `.mockery.yaml`, regenerate with `make mocks`) generates mocks for Store, Queue, Scheduler, **and `github.Client`** into `internal/*/mocks/`. Tests for Store/Queue/Scheduler drive the generated mocks by expectation. Tests for `github.Client` do **not** — the checker/scheduler/reconciler packages keep hand-written stateful *fakes* (seed a map, the fake computes the answer) and merely **embed `mocks.MockClient`** so an interface addition is absorbed by regeneration instead of breaking three files. Override in the fake every method your test needs; anything un-overridden panics with testify's "no return value specified", which is deliberate — a silent zero value is how the IMPL-0013 P4 vacuous-assertion bug happened. Do not rewrite the fakes into expectation plumbing: six behaviors (four of them list-then-act pairs) depend on the fake semantics; see IMPL-0021 task 7.1 for the table.
- **mockery v2 cannot load this module.** v2's final release (2.53.6) is built against go1.25 and fails with *"package requires newer Go version go1.26"* on every invocation — `make mocks` was silently broken until the v3 upgrade, which is why the Phase-0 `Store.UpsertIfMissing` mock was hand-extended. There is still **no CI gate** diffing regenerated mocks against committed ones, so a stale mock will not fail a PR; regenerate by hand after touching an interface.
- **Test-local recording fakes for queue/store (post-IMPL-0016)** — when a test only needs to observe whether the system-under-test enqueued or persisted something, the convention is to define a file-local `recordingQueue` / `fakeStore` type that satisfies `queue.Queue` / `store.Store` with the minimum behaviour for the assertion. These are NOT backend replacements (DESIGN-0018 deliberately rules out shipping a new in-process test backend); they're per-file recorders. Reference impls live in `internal/checker/sweep_test.go`, `internal/scheduler/sweep_test.go`, `internal/webhook/handler_test.go`, `internal/worker/worker_test.go`. For full-behaviour parity (Subscribe pump, BRPOP semantics, etc.), use the valkey integration tests under the `integration` build tag.
- `httptest.Server` is used for GitHub API mocks in `internal/github/client_test.go`.
- Note: `t.Parallel()` cannot be used with `t.Setenv()` in Go 1.25+ (panics at runtime). Config tests avoid `t.Parallel()`.
- Counter assertions: `prometheus/client_golang/prometheus/testutil.ToFloat64(metric.WithLabelValues(...))` for value inspection; `metric.Reset()` between tests when state must be isolated.
- Coverage target: 60% (threshold: 40%), tracked via Codecov.
- Coverage ignores: `main.go`, `docs/`, `scripts/`.

## Engine and Loader Subtleties

- **Strict-mode loader behavior** — when `cfg.Scope != nil` and the user declares no rules, the loader does **not** fall back to `BuiltinDefaults().FileRules`. This is the only way the contract "every rule must declare its own scope" can hold. See the `switch` in `loader.go.hclConfigToPolicy`.
- **File-rule double-iteration** — `engine_policy.go` iterates over `policy.FileRules` in two passes: `findActionableRules` (primary) and `runReconcilers` (post-check). Counter increments belong only to the primary pass; `runReconcilers` short-circuits on scope/ignore mismatch silently. Forgetting this leads to double counts on `OutOfScopeTotal{level=rule}` and `IgnoredTotal{scope=rule}`.
- **Scope vs. ignore precedence** — both gates run before evaluation. Scope is checked first (out-of-scope skips counted in `OutOfScopeTotal`); ignore is checked second (skipped repos counted in `IgnoredTotal`). The two counters never both increment for the same rule on the same repo.
- **Phantom `gopls` diagnostics** — when adding a new file in `internal/checker/`, `gopls` may show `undefined: Engine` errors for a few seconds while the cache rebuilds. Real compile/test results are authoritative; ignore the IDE warnings if `make lint` and `make test` pass.
- **Backend defaults post-IMPL-0016** — `internal/config/config.go.loadBackendConfig` defaults `STORE_BACKEND=postgres`, `QUEUE_BACKEND=valkey`, `SCHEDULER_BACKEND=valkey`. `validateBackends` rejects any other value via the `validateBackend` helper, which carries a `deprecatedBackends` map for migration-aware messages on `memory`/`ticker`. `STORE_DSN` and `QUEUE_VALKEY_DSN` are required env vars; tests that call `config.Load()` MUST `t.Setenv` placeholder DSNs or Load returns a joined-errors error. See `internal/config/config_test.go.TestLoadDefaults` for the canonical placeholder pattern.
- **Guardian block strict decode (INV-0010, appVersion 1.9.1)** — `guardian {}` decodes through `guardianBodySchema` + `Content()`, so unknown attributes fail load with "Unsupported argument" (they were silently swallowed by `JustAttributes()` before). Adding a `GuardianConfig` field needs THREE spots in lockstep: the `guardianBodySchema` attribute list, a `setGuardianAttr` case, and a `mergeGuardianConfig` carry — miss the merge and HCL values silently vanish (that was the `auto_close_pr` bug: field + env override existed, decode + merge didn't). Env overrides still win via `applyEnvOverrides` running last.
- **Absent check mode + when-gates (IMPL-0019, DESIGN-0020)** — a fourth file-rule mode `check = "absent"` (actionable iff **any** `paths` exist on the default branch; remediation is a `DeleteFile` PR on the reconcile branch via `removeForbiddenFiles`) and a `when { rule_satisfied = "<sibling>" }` gate. Key invariants: (1) **gate memoization lives on `gateEvaluator`, NEVER on `*Engine`** — the engine is shared across worker goroutines, so per-repo-check mutable state on it would race; `newGateEvaluator` is constructed inside `checkRepoWithPolicy` and threaded to both passes. (2) **Gate is content-only + default-branch-only + fail-closed** — `ruleSatisfiedOnDefault` is `evaluateRule` minus the open-PR short-circuit and minus scope/ignore; a referee eval error closes the gate (`reason="error"`), never opens it. (3) **`RuleGateClosedTotal` increments only in the primary pass** (`findActionableRules`); `runReconcilers` reuses the memoized `gateOpen` result silently — same double-iteration contract as scope/ignore. (4) **Absent-actionable increments `FilesForbiddenPresentTotal`, not `FilesMissingTotal`** (see `recordActionable`). (5) **Inverse-orphan restoration** (`drift.go.restoreInverseOrphans`): an absent rule that stops being actionable but whose forbidden file the reconcile branch already deleted is restored from default-branch content — mirror of add-mode orphan cleanup, fail-safe with `PROrphanLeftTotal`. (6) Absent rules **forbid** `target`/`template`/`assertion`/`reconcile` at load. (7) `ExtractWatchedPaths` unions a gate's referee paths AND the gated rule's own paths into the push-watched set, and `hasWatchedFileChanges` now scans `commit.Removed` (a removed `renovate.json` flips a gate).

## Release

GoReleaser builds for linux/darwin on amd64/arm64 (CGO disabled). Releases are GPG-signed. Semantic versioning via PR labels (`major`, `minor`, `patch`, `dont-release`). One semver label is required to merge — the workflow fails without it.

**Helm chart distribution (DESIGN-0011, Approved):** `oci://ghcr.io/donaldgifford/charts/repo-guardian` and `oci://<ECR>/repo-guardian-chart` (multi-registry since the multi-registry-publish refactor). Public visibility on GHCR, private on ECR. Both signed with cosign keyless and ship SLSA Level 3 provenance. The legacy chart-releaser → `gh-pages` flow is deprecated because `gh-pages` serves the mkdocs site. Chart `version` is independent of binary `appVersion`; do not auto-bump on every binary release.

**Changelog generation (IMPL-0010):** `git-cliff` (mise-managed, currently `2.12.0`) drives both the root `CHANGELOG.md` and the chart-only `charts/repo-guardian/CHANGELOG.md`. Two configs: `cliff.toml` (root) and `charts/repo-guardian/cliff.toml` (chart). The chart config is gitignored from the `.tgz` via `charts/repo-guardian/.helmignore` (build-time only). The chart `CHANGELOG.md` itself is regenerated on-the-fly by the publish workflow before `helm package`, so the published artifact always ships with a current changelog. Invocations: `git-cliff --config cliff.toml --output CHANGELOG.md` (root) and `git-cliff --config charts/repo-guardian/cliff.toml --include-path 'charts/**' --output charts/repo-guardian/CHANGELOG.md` (chart). The `--include-path` filter lives at invocation time, not in config.

**Publish workflows — per-registry split.** `release.yml` is the orchestrator: it runs `bump-version` (PR-semver-label-driven) and `release` (goreleaser binary release), then **always** calls `ghcr.yml` and `ecr.yml` as reusable workflows (`uses: ./.github/workflows/ghcr.yml`, `secrets: inherit`). Each per-registry file has the same shape: an `image` job gated on `inputs.tag != ''` (so it only runs on actual binary releases) plus a `chart` job that runs unconditionally and is idempotent via the `helm pull` precheck. Chart-only changes (PR labeled `dont-release`) still publish the chart because the chart job doesn't gate on the binary release. Each registry workflow also exposes `workflow_dispatch` with `tag` + `dry_run` inputs for ad-hoc republishes. Both files call the SLSA reusable workflow (`slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@v2.1.0`) twice — once for the image, once for the chart. Image builds use `docker/bake-action@v7` against `docker-bake.hcl`'s registry-agnostic `release` target; tags + labels come from `docker/metadata-action@v6` so the same bake file pushes to both registries. ECR auth uses GitHub OIDC + `aws-actions/configure-aws-credentials@v4` + `aws-actions/amazon-ecr-login@v2`; a leading `aws-auth` job extracts the ECR auth token (12h validity), masks it with `::add-mask::`, and outputs it for the chart job and both SLSA reusable workflows (which take `registry-username: AWS` + `registry-password` as a secret input).

**Release pipeline post-mortem (June 7 – July 8 2026, PRs #143–#146):** every push-triggered `release.yml` run failed silently from the day the per-registry split landed until v1.8.2 shipped. Four stacked bugs, each masked by the previous one — and none catchable by actionlint:

1. **Nested reusable-workflow permission ceilings.** The caller job's `permissions` block in `release.yml` is a hard ceiling for every job in the called workflow *and everything it calls*. The SLSA generator's internal `generator` job requests `{id-token: write, actions: read, packages: write}` — `packages: write` even on the ECR path (attestations upload to ghcr.io regardless of the target registry). The whole chain must grant the union. Violations fail the run at startup with **zero jobs created** (`startup_failure`), and `if:`-gated jobs are still graph-validated — the disabled `publish-ecr` call broke the entire run.
2. **`startup_failure` is silent.** No jobs means no failed check anywhere anyone looks; the breakage went unnoticed for a month because manual `workflow_dispatch` of `ghcr.yml` worked fine (direct dispatch has no caller ceiling). Diagnostic path: `gh run view` only says "workflow file issue"; the actual validation error (e.g. `The nested job 'generator' is requesting 'packages: write', but is only allowed 'packages: none'`) is rendered only on the run's web page. If release.yml is ever refactored, verify the next push-triggered run *creates jobs*, don't just trust green PR CI.
3. **Never inline `${{ steps.x.outputs.metadata }}` into `run:` scripts.** The bake metadata JSON contained a character that broke single-quoting → `syntax error near unexpected token '('` → the v1.8.2 image pushed but unsigned with no provenance. Fix shape: pass through `env:` (`BAKE_METADATA: ${{ ... }}`) and read with `jq ... <<< "${BAKE_METADATA}"` — env values are never shell-parsed. **That fix shape was itself incomplete and broke v1.11.0 — see the bake-metadata size ceiling below.**
4. **Wrong step id in job outputs skips silently.** `ghcr.yml`'s image job outputs referenced `steps.bake.outputs.digest/published`, but those are written by the `Capture image digest` step (`id: digest`); bake only outputs `metadata`. Outputs were always empty, so `image-slsa`'s `if: needs.image.outputs.published == 'true'` never fired — **no GHCR image had SLSA provenance until 2026-07-08**, invisibly, because a skipped job isn't a failure. `ecr.yml` had the correct id (copy-paste divergence between the twins). When the two registry workflows are edited, diff them against each other.

**Bake metadata is too big to be an environment variable (v1.11.0, PR #172).** The v1.8.2 fix above — hand `steps.bake.outputs.metadata` to the script through `env:` — is safe but not durable, because the blob outgrew `execve`. bake defaults to `provenance=mode=max`, and mode=max embeds the whole GitHub event payload in the attestation; on a `push` that payload carries `head_commit.message` **and** `commits[0].message` (the same text twice), and the payload is embedded once **per build platform**. So one squash-merge commit message is multiplied ×4. PR #172 squashed 38 commits into a 24,756-byte message → `BAKE_METADATA` = 133,602 bytes → past Linux's 131,072-byte `MAX_ARG_STRLEN` → `##[error]An error occurred trying to start process '/usr/bin/bash' ... Argument list too long`. bash never started, so the step's own `exit 1` guard never ran; the image pushed **unsigned with no SLSA L3 provenance** (buildkit's own SLSA v1 attestation *was* still attached in the registry — that comes from the build, not from CI). The measured trend was #168 18.5KB → #169 19.8KB → #171 23.1KB (97% of the limit) → #172 24.8KB, i.e. we'd been grinding against the ceiling for three releases. **Fix: extract the field in the expression layer** — `DIGEST: ${{ fromJSON(steps.bake.outputs.metadata).release['containerimage.digest'] }}` — so only a 71-char digest reaches the environment. This keeps the "never let the shell parse registry-derived text" property, and is immune to both commit-message length and platform count. Do NOT "fix" this by writing shorter commit messages or by disabling provenance: `BUILDX_METADATA_PROVENANCE=disabled` would also work but only suppresses the redundant copy echoed back to CI, and shorter messages just reset the countdown. Note the diagnostic trap: `jq -r '.release."containerimage.digest"'` was **never wrong** — the path resolves correctly against the real metadata, so reading the jq expression teaches you nothing. The `##[error]` line is 600 lines below the step in the raw log; fetch it with `gh api repos/{owner}/{repo}/actions/jobs/{job_id}/logs`.

The SLSA reusable workflow must stay referenced by a semver **tag** (`@v2.1.0`); renovate proposed pinning it to a commit SHA (closed PR #106), but the trusted builder verifies its own ref at runtime and digest refs fail the provenance job. If renovate re-attempts the pin, add a packageRule exception for `slsa-framework/slsa-github-generator`.

**Cosign + helm dual-login gotcha (IMPL-0010 post-mortem, PR #61):** `helm registry login` writes to `~/.config/helm/registry/config.json`. Cosign reads `~/.docker/config.json`. The two stores are disjoint, so a workflow that only does `helm registry login` will have helm pushing fine but cosign signing failing with `UNAUTHORIZED: unauthenticated`. Fix is to add `docker/login-action@v4` for cosign's auth path BEFORE the cosign step. Both logins are kept — they serve different binaries. This bit us on the 0.3.0 first publish; rolled forward to 0.3.1 with the fix. Documented yank-by-roll-forward (don't delete-and-resurrect a published version) was exercised in practice.

**GHCR new-package visibility:** First push from a workflow auto-creates the GHCR package as **private**. Consumers' anonymous `helm pull` will 401 until the maintainer flips the package visibility to **public** via the GHCR settings UI. There's no API for this flip; it's a one-time manual step per package. After flipping, subsequent publishes inherit the public visibility setting — no re-flip needed on every chart version bump.

**Chart template namespace stamping (PR #67, chart 0.3.1 → 0.3.2):** Every template in `charts/repo-guardian/templates/` MUST include `namespace: {{ .Release.Namespace }}` in its `metadata` block. Helm convention says skip this because `helm install --namespace X` sets it at apply time, but that breaks the kustomize+helm via ArgoCD consumption pattern: `helm template` doesn't write namespace into rendered manifests, kustomize's namespace transformer doesn't reliably propagate to helmCharts output, and ArgoCD then applies the rendered resources to whatever `spec.destination.namespace` is configured (often the wrong one). Symptom in the homelab: chart resources landed in `argocd` namespace while OnePasswordItems with explicit `metadata.namespace: repo-guardian` landed correctly — Deployment couldn't reach its secrets. RoleBinding subjects also need explicit `namespace:` for the same reason. Verify after any new template: `helm template ... | grep -E '^kind:|^  namespace:'` should show every kind paired with the expected namespace.

**ArgoCD `app get` NAMESPACE column is misleading.** When troubleshooting placement, `argocd app get <name>` shows a NAMESPACE column that doesn't always reflect where resources actually live. Use `kubectl get <kind> -A | grep <name>` to find the real namespace, then compare against `spec.destination.namespace` on the Application. Resources WITHOUT explicit `metadata.namespace` go to the destination namespace; resources WITH it go where they say (which is why our OnePasswordItems landed correctly while helm-templated resources didn't).

**`DRY_RUN` precedence at runtime:** env var (set on the Deployment) overrides any `dry_run` from HCL or built-in defaults via `applyEnvOverrides` running last in `Load()`. A kustomize patch or Helm values setting `DRY_RUN=true` will silently keep the engine in dry-run regardless of the policy file. Always check `kubectl get deploy ... -o jsonpath='{.spec.template.spec.containers[0].env[?(@.name=="DRY_RUN")]}'` first when the binary appears to be reading the wrong policy state.

**Idempotent file commits on the reconcile branch (INV-0003, appVersion 1.4.1):** `internal/github/client.go.CreateOrUpdateFile` does GET-on-target-branch first, then either skips (identical content), updates with the existing blob `sha` (different content), or creates fresh (file missing). Before this fix the wrapper called `Repositories.CreateFile` unconditionally, so a second reconcile against a repo with an open `repo-guardian/add-missing-files` branch would 422 with "sha wasn't supplied." If you ever rename or rewrite this function, preserve the three-branch behavior — the package-level `GetContents(ctx, owner, repo, path)` helper is *default-branch-only* and will not protect you against the same bug if you swap to it.

**IMPL-0013 Phase 4 — sticky reconcile-log PR comment.** `upsertReconcileLog` posts a markdown table comment with per-rule status (`satisfied on main` / `still actionable` / `orphan removed from branch`) on every reconcile that finds an existing repo-guardian PR. **Idempotency via content hash:** `renderReconcileLog` embeds an HTML comment `<!-- repo-guardian:reconcile-log:hash:<8-hex> -->` (SHA-256 truncated, computed over the sorted rule-status pairs only) on row 1 of the rendered body. The skip-on-match check in `upsertReconcileLog` uses `strings.Contains` against the hash tag — NOT full-body byte equality — so identical-state sweeps converge to a single `UpsertPRComment` API call despite the human-readable RFC3339 timestamp changing between sweeps. Verified end-to-end by `TestStickyComment_NoUpsertOnIdenticalState`. If you ever extend the hash domain (e.g., to include orphan-cleanup metadata), bump the hash-marker version alongside the row-0 marker. Wired into three call sites: (1) `createOrUpdatePRFromPolicy` after orphan cleanup + body refresh; (2) `autoClosePR` as the final close-comment with an "Auto-closing" footer (same marker — the comment persists on the closed PR); (3) the AutoClosePR=false convergent branch so operators see why the PR is intentionally stuck. The rendered body is inline-built via `renderReconcileLog` (markdown table + RFC3339 timestamp), not routed through `internal/template/` — there's no operator-tunable surface for this comment today and the renderer's compile machinery would be overkill for a < 1KB markdown blob. `buildReconcileLogEvents` joins `allRules`, `actionable`, and `removedOrphans` into a flat `[]reconcileLogEvent` for the table; orphans get their own bucket so the cleanup action is visible in the log. The marker `<!-- repo-guardian:reconcile-log:v1 -->` is shared with the close path — there's exactly one sticky reconcile comment per PR, and it gets edited in place across the PR's lifetime.

Contract assertions live inline in each backend's `_integration_test.go` under the `integration` build tag (e.g., `internal/scheduler/valkey/valkey_integration_test.go` covers `Schedule_Fires`, `Stop_Idempotent`, `Schedule_AfterStop_Errors`; `internal/queue/valkey/valkey_integration_test.go` covers `EnqueueDequeue`, `SubscribeContextCancel`, `CloseUnblocksSubscribe`). If a second backend is added later, factor the sub-test bodies into a `contract_test.go` helper at that point; don't pre-build the helper for a single implementation.

**IMPL-0023 (DESIGN-0022) — the posture-state contract.** Compliance is state read back from Postgres, not counters incremented at check time. The invariants:

- **Posture flows one way: worker → `rule_state` → leader-only export → gauges.** `worker.processJob` writes per-rule outcomes via `writeBackRuleStates` (best-effort, same never-propagate contract as the repo-state write-back — the queue stays the source of truth for "did we do the work"); `checker.PostureExporter.Export` runs under the same SETNX leader election as stale-sweep and republishes `repos_actionable{rule_name,org}` / `repos_tracked{org}` / `repos_unmeasurable{org,reason}` every `POSTURE_EXPORT_INTERVAL` (60s). Non-leaders publish **nothing**, not stale values. Export reads BEFORE `ResetPosture()` — reset-first would blank every series for the duration of the query and a scrape in that window reads as a vanished fleet. On read error the previous values persist: for a gauge, last known truth beats a confident zero.
- **Query posture with `max by (...)`, never `sum`.** A demoted replica keeps serving its last values until restart, so `sum` double-counts through every failover. Fleet totals are `sum(max by (org) (...))` — inner collapses replicas, outer adds orgs; reversed it reports the largest org and looks plausible. `TestSuite_PostureQueriesDedupeAcrossReplicas` pins the generated dashboards.
- **Compliance reads "no data" when nothing is tracked, never 100%.** Dashboard guard `and on() (sum(max by (org) (repo_guardian_repos_tracked)) > 0)` mirrors `report.CompliantPercent` returning `(0, false)` on `Tracked <= 0`. A dead exporter must not report a perfect fleet.
- **The taxonomy (INV-0013 Finding I) is one datasource and one tier per panel.** Business (E1 KPI/E2 detail), service+infra (E3 system), evidence (E4 Loki). No repo label on any metric — "which repository" is answered by logs only (Finding G). Full map: `docs/operations/scaling.md` §Compliance posture; generation: `docs/operations/monitoring-generation.md`.
- **Dashboards and alerts are GENERATED (`repo-guardian monitoring generate`), and the committed tier is drift-gated.** `internal/monitoring` (model) / `monitoring/alert` (catalogue-as-data, mechanism-gated) / `monitoring/dashboard` (foundation-sdk panel library) / `monitoring/emit`. `make monitoring-generate` rewrites `contrib/generated/`; `make lint-monitoring` regenerates into `build/` and `diff -r`s (NOT `git diff --exit-code`, which is blind to untracked files — the gate must fail on an added dashboard too). Hand-editing a generated file turns CI red. E4's LogQL matchers are constants in `dashboard/e4.go`; `TestLogLines_AreStillEmittedByTheBinary` walks `internal/` and fails if a matched log line stops being emitted — a matcher that stops matching renders as "this never happens". The catalog-parse line is additionally locked verbatim by `internal/reconciler/log_contract_test.go`.
- **Rare-event `> 0` alerts need `alert.firstOrIncrease`.** `increase()` cannot see a counter's first-ever increment (no earlier sample to subtract), and for "a repository lost access" the first occurrence may be the only one. `TestCatalogue_RareEventAlertsCatchTheFirstIncrement` pins which alerts carry the guard and that threshold alerts (PRBurst) do NOT — a new counter at 1 is not a burst. The chart's PrometheusRule mirrors the guarded expressions by hand; keep the two in step.
- **The four unlabelled `properties_*` counters are gone (Phase 7).** `properties_prs_created_total` folded into `prs_created_total{org}` — the reconcilers now increment the engine's counter, so github-action deployments see it step up post-upgrade. `RepoGuardianPropertiesPRBurst` deleted (folded, it was PRBurst under another name); `MechanismCustomPropertiesGHA` survives gating nothing, as a reported fact about the write path.

**Transport-ordering contract (shared IMPL-0022 / IMPL-0023): otelhttp OUTERMOST, above the rate-limit transport, above ghinstallation.** All three GitHubClient constructors funnel through `instrumentedClient` so the order cannot drift. Why it is load-bearing: the rate-limit transport *refuses* to send under the reserve (returns `*ThrottledError` in place of a response); with otelhttp on top that refusal is still an attempt and lands in the client histogram with `error.type` and no status code — the residual throttle signal that replaced `github_rate_limit_wait_*`. Underneath, deferred calls would vanish from the metrics and a throttled installation reads as idle. `TestTransportOrder_ThrottledRequestIsStillMeasured` pins it by sample count, not attributes. Related trap: go-github's own pre-check ALSO short-circuits above the transport chain when its header cache saw remaining=0, so those calls are never measured anywhere — `http_client_request_duration_seconds_count` under-counts exactly when throttled; use `queue_delayed_total{reason="rate_limit"}` for throttle volume.

**IMPL-0022 (DESIGN-0021) — the delayed-requeue contract and the one-mechanism rule.** The single most important invariant in the rate-limit path:

- **NOTHING BLOCKS IN-HANDLER. EVER.** A worker holding an in-flight claim must never sleep waiting for a resource. It returns a `*queue.RetryAfterError{After, Reason}`; the queue parks the job in the delayed ZSET with that due-time and frees the slot. This is not a style preference — sleeping in-handler is how INV-0012 finding I happened: the transport slept up to an hour while `JOB_ACK_TIMEOUT` was 5m, so the reaper cloned the still-running job every `REAPER_INTERVAL`, amplifying load against an already-exhausted budget. If you are about to add a `time.Sleep`, a blocking retry loop, or a "wait for the circuit breaker" to anything reachable from `worker.processJob`, add a deferral instead. The one surviving sleep is the reactive 403/secondary-limit retry in `internal/github/ratelimit.go`, capped at `maxRateLimitSleep = 60s`, which **must stay below `JOB_ACK_TIMEOUT`** — a static test guard enforces this and it is deliberate, not incidental.
- **One throttle mechanism, not four.** Pre-IMPL-0022 there were the transport sleep, the sweep reserve gate, the BudgetTracker, and the reactive retry — none composing, one of them (the tracker) completely inert. Now there is one: the transport signals, the worker defers, the reaper promotes. Do not add a second gate "for safety." If a new backpressure source appears (secondary limits, a per-tenant quota, an upstream 429), it becomes another `Reason` on `RetryAfterError`, not another layer.
- **Four Valkey keys, all defaulted in one place.** `jobs` (LIST), `in-flight` (ZSET scored by claim nanos), `delayed` (ZSET scored by due nanos), `lock:reaper` (STRING). `Options.applyKeyDefaults()` is the single construction point — the DESIGN-0015 per-installation-partitioning hook. **A job is in exactly one key at every instant**; the moves are Lua (`deferScript`, `promoteScript`, `requeueScript`) so no window exists where a job is in two or neither. `TestValkey_ExactlyOneKeyInvariant` pins this.
- **`Attempts` increments on every redelivery** — worker deferrals (`deferInFlight`) and reaper requeues (`requeuePayload`) alike. At `MAX_JOB_ATTEMPTS` (default 10) the next delivery calls `dropExhausted`: terminal `StatusError` to `repo_state` naming the env var, `queue_attempts_exhausted_total`, then **return nil so the queue acks and drops**. Returning an error there would re-nack and rebuild the infinite loop the cap exists to break; the stale sweep is the recovery path.
- **A deferral is not a failure.** It skips `ErrorsTotal` and skips the `repo_state` write-back entirely — the check never ran, so there is no outcome to record. Recording one would make a throttled repo look freshly-checked and suppress its next sweep.
- **`REAPER_INTERVAL` does double duty** — stuck-job reaping and delayed promotion share one leader election and one timer (DESIGN-0021 OQ3). Promotion therefore lags due-time by up to one interval. Do not add a separate promotion ticker.
- **Throttle detection MUST go through `github.AsThrottled(err)`.** go-github v68 has a fourth signal path nobody designed for: `checkRateLimitBeforeDo` short-circuits *above* our transport with its own `*gh.RateLimitError` whenever its response-header cache saw remaining=0, and the `bypassRateLimitCheck` context key is unexported so it cannot be disabled. `AsThrottled` normalises both shapes. A bare `errors.As(err, &ThrottledError{})` silently misses the pre-check path — `internal/checker/ratelimit_chain_test.go` is the regression test, and it found this by failing.

**INV-0015 — repository parking and the subset invariant (PR #177).** `repo_state.active` gates whether a repository is offered to the stale sweep at all. `Store.Deactivate` parks; **only `UpsertIfMissing` (i.e. discovery) un-parks**, via `ON CONFLICT ... DO UPDATE SET active = true WHERE NOT repo_state.active`. Rows are kept, never deleted.

- **The subset invariant is the whole design.** Parking is stable only when the check path's skip conditions are a **subset** of discovery's filters, because discovery is the only un-parker. `checker.skipReason` returns `(reason, durable)`; `durable` is true only for `archived` and `fork`, which `Discoverer.discoverInstallation` also filters — and off the *same* `policyCfg.Guardian.SkipArchived/SkipForks` fields, so the relation is exact rather than coincidental (flag off → neither skips → nothing parks). `empty` is deliberately NOT durable: discovery does not filter empty repos, so parking one would have discovery re-activate it every pass and the two would churn at `DISCOVERY_INTERVAL` (1h) instead of settling. `TestPool_EmptyRepo_IsSkippedButNotParked` pins this. **Adding a fourth skip reason means checking `discoverInstallation` first.**
- **`WHERE active` must parenthesize the freshness disjunction.** `AND` binds tighter than `OR`, so `... OR policy_version <> $2 AND active` would gate only the last arm and un-park every repo the moment the policy hash changed. `TestPostgresStore_DeactivateExcludesFromSweep` covers exactly this.
- **`UpdateRepoState` must never reset `active`.** A parked repo writes state on its way out; an upsert that touched the flag would un-park it immediately. `TestPostgresStore_UpdateRepoStateDoesNotUnpark` is the guard.
- **Classify-then-dispose, mirroring IMPL-0022.** `worker.processJob` runs `AsThrottled` → defer, then `ghclient.IsAccessDenied` → park, then `checker.AsSkipped` → park. Order matters: a secondary rate limit is also a 403, so `AsThrottled` must be checked first. `park` returns nil so the queue acks and drops, same contract as `dropExhausted`.
- **A skip is not an error.** Access-denied parks write `StatusError` with the API failure in `LastError`; archived/fork parks write `StatusSkipped` with the bare reason. The reason goes in `LastError` despite not being an error because there is no `park_reason` column and that field is what makes `SELECT ... WHERE NOT active` answer *why*.
- **One metric, `reason` from birth.** `repo_guardian_repos_parked_total{org, installation_id, reason}`. The alert selects `reason="access_denied"` — archived/fork parks are routine and would page on every onboarding sweep. The helm-unittest locks that selector, not just the alert name.
- **The nil-vs-empty `*CheckResult` rule (IMPL-0023).** `worker.park` takes a posture result, and the two park families need OPPOSITE values — that is why it is a parameter. `access_denied` passes **nil**: we could not read the repository, learned nothing about its rules, and clearing them would make an unreadable repo look compliant. `archived`/`fork` pass **`&checker.CheckResult{}`** (empty, non-nil): we read the repository fine and know definitively no rule applies, so its `rule_state` rows must clear or the parked repo counts against compliance forever — parking is exactly the state in which it will never be re-checked and corrected. Getting this backwards is silently wrong in BOTH directions, and nothing crashes: nil-where-empty-belongs freezes stale posture rows under a parked repo; empty-where-nil-belongs wipes real posture on a transient 403. Downstream, `writeBackRuleStates` treats nil as "write nothing" and empty as "delete-not-in with an empty keep-set". The engine's own error paths return `(nil, err)` for the same reason.

**Chart alerts are promtool-checked via `make lint-alerts-chart`, not helm-unittest.** helm-unittest asserts that an alert *renders*; it passes 105/105 against syntactically invalid PromQL (verified by breaking `RepoGuardianStaleOpenPRs`). `lint-alerts` now has two halves — `lint-alerts-contrib` (the standalone `contrib/prometheus/alerts.yaml` recipe) and `lint-alerts-chart`, which renders the chart, extracts `spec.groups` with `yq`, and runs `promtool check rules`. The CI `alerts` paths-filter covers `contrib/prometheus/**`, `charts/repo-guardian/templates/prometheusrule.yaml`, `charts/repo-guardian/values.yaml`, and `Makefile`; before that widening the job was gated on `contrib/prometheus/**` alone, so **every chart-alert change since the job was added showed `skipping`** and no chart alert was ever parsed. The chart half guards against a vacuous pass explicitly: `promtool` exits 0 on "0 rules found", so the target counts rules with `yq` and fails if the render is empty.

**IMPL-0020 (INV-0011 A1+A2) — two custom-properties contracts.** Two invariants a future edit must not regress:

- **catalog.Parse never returns destructive defaults.** `catalog.Parse(content, annotationProps)` returns `(*Properties, error)` with THREE outcomes: valid Component → Properties; unparseable YAML → wrapped parse error; valid non-Component entity → `catalog.ErrNotComponent` sentinel. Both error outcomes carry a nil `*Properties`. `custom_properties.go.Reconcile` maps BOTH to skip-without-writing (parse error logs Warn + increments `CatalogParseFailedTotal{org}`; ErrNotComponent logs Info, no counter), so a malformed or non-Component `catalog-info.yaml` can never PATCH `null` over the managed set. The `Unclassified` defaults come ONLY from `catalog.Defaults()`, called on the genuinely-missing-file path (`catalogFound == false`). Do not resurrect a "return defaults on parse failure" shortcut — that was the A1 data-loss bug. This skip-abort is also a prerequisite for IMPL-0021's A3 (clear-on-file-removal).
- **set-custom-properties.tmpl uses env-indirection, never inline value interpolation.** Property VALUES (repo-controlled via `catalog-info.yaml`) reach the generated workflow only through the `env:` block, rendered by the `yamlq` template helper (single-line double-quoted YAML scalar, control-char escaped, rejects `${{`). The `run:` script references them as quoted `"$RG_PROP_*"` shell vars via the `propenv` helper (property name → `RG_PROP_`-prefixed identifier, non-`[A-Za-z0-9_]` → `_`). NEVER interpolate a `.Catalog.Properties` value directly into an `-f 'properties[][value]=...'` arg — that inline shape was the A2 command-injection vector. Property NAMES stay inline (single-quoted) because policy validation constrains them to `^[a-zA-Z0-9_.-]{1,75}$`. Both helpers live in `internal/template/helpers.go`; the injection regression + byte-exact YAML round-trip tests are in `internal/rules/registry_test.go`.

**`StaleSweeper` replaces per-tick repo enumeration (IMPL-0011 P5):** `internal/checker/sweep.go` implements the post-Phase-5 sweep handler: query `Store.StaleRepos(freshness, currentPolicyVersion, batch)` and `Queue.Enqueue` each candidate. The reserve gate it originally carried was removed in IMPL-0022 Phase 6; what remains is `sampleRateLimit`, one `Client.RateLimitRemaining` call per installation per sweep that exists ONLY to feed the `rate_limit_remaining{installation_id}` gauge (that call sets the gauge as a side effect and is its sole producer — delete it and `RepoGuardianRateLimitNearExhaustion` starts consuming an unfed series). The legacy "iterate every installation, list every repo, push to channel" pattern is gone. `policy.Version()` produces a stable hash of the loaded policy (used as the freshness gate) and is the only consumer of the policy-version state; if you change the policy struct, validate this hash still discriminates intended changes from cosmetic ones. The sweep handler is wired in via `Scheduler.Schedule(name="sweep", interval=...)` from `cmd/repo-guardian/main.go`.

**Chart 0.4.0 / appVersion 1.5.0 (IMPL-0012):** breaking chart values change — legacy `templates.codeowners`/`dependabot`/`renovate` slots removed in favor of `templates.files: <name>: <content>` map. New keys: `templates.existingConfigMap`, `templating.vars`, `templating.strict`. Embedded `.tmpl` files were rewritten from `OWNER_VALUE`-style to dotted-path Go template syntax; GHA `${{ ... }}` expressions in any custom template must be wrapped in a backtick-raw-string action. PR templates (title/body/labels) configurable at three HCL scopes (`defaults.pr`, `rule.pr`, `reconcile.pr`) with field-by-field inheritance and `inherits=false` short-circuit. Migration recipe in `docs/operations/template-migration.md`; homelab smoke runbook in `charts/repo-guardian/docs/homelab-smoke.md`.

**`PRConfig` vs `PRTemplate` in `internal/policy` (IMPL-0012):** these are deliberately different shapes and easy to confuse. `PRConfig` is the *raw HCL block* — `Title`/`Body` are `*string` (presence-distinguished), `Labels` carries a sidecar `LabelsSet bool`, and `CompiledTitle`/`CompiledBody` cache the post-load parse output. `PRTemplate` is the *resolved* output of `ResolveRulePR` / `ResolveReconcilerPR` — `Title`/`Body` are `*tmpl.Compiled` ready for `Render(*PRVars)`. Engine and reconciler call sites consume `PRTemplate`, not `PRConfig`. The `compilePolicyTemplates` pass populates the `Compiled*` fields on `PRConfig` at load time; resolution lifts those into a fresh `PRTemplate` via `asTemplate`.

**Helm chart README is generated from `README.md.gotmpl`** — `make helm-docs` (and the chart-publish workflow) regenerates `charts/repo-guardian/README.md` from the template. Adding handwritten content directly to `README.md` is silently stripped on the next regeneration. Session post-mortem: the IMPL-0012 "Security considerations" section was first added to `README.md` and lasted exactly one `make helm-docs` invocation before disappearing. New static content must go into `README.md.gotmpl`. Backtick-escape rule still applies inside `.gotmpl` for literal `{{ env "VAR" }}` examples in markdown code blocks.

**`docz update <type>` regenerates indices AND TOCs** — running `docz update impl design` rewrites the section README tables based on each doc's frontmatter `status:` field and also incidentally regenerates the `<!--toc:start-->` blocks inside any doc whose body has drifted from its TOC. Watch the diff and don't be surprised when an unrelated DESIGN gets a TOC bump.

**`Renderer.Raw` is gone (post-Phase 3)** — the Phase 2 raw-passthrough mechanism for GHA `${{ ... }}` templates was replaced in Phase 3 with the backtick-escape rewrite. The `Compiled` struct holds only `tpl *texttemplate.Template`; there is no `raw` field, no `Raw()` constructor on `Renderer`, and `Render` does not have a non-template fallback path. Any future templates that need to emit literal `{{` must use the same `{{`+backtick+...+backtick+`}}` wrapper.

**CI paths-filter convention (PR #77):** `.github/workflows/ci.yml` runs a `changes` setup job using `dorny/paths-filter@v3` that emits boolean outputs for `go`, `docker`, `helm`, `workflows`. Every downstream job MUST declare `needs: changes` and an `if:` gate against the relevant outputs — otherwise the docs-only-skip benefit silently regresses. Reference matrix: `lint` runs on `go || helm || workflows`; Go-only jobs (`test-go`, `security`, `build`) run on `go || workflows`; `docker-build` on `go || docker || workflows`; helm jobs (`helm-unittest`, `helm-test`) on `helm || workflows`. `labeler` is the only exception — it runs unconditionally because labeling is cheap and informs every PR. Skipped jobs gated by `if:` on the job (not via workflow-level `paths:`) satisfy branch-protection required checks; no protection changes needed when adding new gated jobs.

**Helm CLI semantics drift in CI (PR #76):** two gotchas bit the helm-unittest job when migrating off the third-party `d3adb5/helm-unittest-action@v2`. (1) `helm plugin install --version "X.Y.Z"` on helm 3.20+ triggers verify mode; the helm-unittest source has no provenance data, so install fails with "plugin source does not support verification." Pass `--verify=false` explicitly, or omit `--version` to install latest (which skips the verify path). (2) `helm unittest --color` is a boolean flag on older plugin versions and an enum (`never|auto|always`) on newer ones — passing `--color charts/foo` on the newer CLI consumes the chart path as the enum value. Easiest fix: omit `--color`, since GitHub Actions terminals enable color via env detection. Both fixes live in the helm-unittest job in `.github/workflows/ci.yml`; if you ever swap that job back to a packaged action, re-verify these behaviors against whatever helm version it pins.

## Rules

These rules must always be followed when working in this repository.

1. **Use the `todo-comments` skill for code annotations.** All TODO, FIX, HACK,
   WARN, PERF, NOTE, and TEST comments must follow the todo-comments format.
   Respect and obey `CLAUDE` type directives — these are binding behavioral
   instructions embedded in code.
2. **Never commit directly to `main`.** All changes go through feature branches
   and pull requests. Use the `git-workflow` skill (`/branch`) to create
   branches with the correct type prefix (feat/, fix/, chore/, docs/, bug/).
3. **Always look for enabled skills to use.** Check what skills are enabled for
   the repo and use those as guiding tools for work.
4. **Always check for make target for a command.** Check if there is an existing
   make target for what you are trying to run. This helps with automating your
   ability to run commands within the scope of safety we have defined.
5. **Use docz for all structured documentation.** When creating design docs,
   investigations, implementation plans, RFCs, or ADRs, use the `docz` skill
   (`docz create <type> "Title"`). Do not create raw markdown files in `docs/` —
   use the docz types configured in `.docz.yaml`.
6. **Use dont-release label for pr's when creating release candidates or pre-releases.**
   The semver bump ci action doesnt support rc-*or pre-releases so we should use
   the `dont-release` label and then manually push the pre-release or rc-* git tag as
   the rest of our tooling supports it. If we do this too often, we should look into
   a replacement or substitute for the semver bump ci action.
