Let me frame this better:

in short - a policy is the who and the what. what org, what repos, what controls. A control is the definition of expected state from the result of a Rule or set of Rules. An example of a control can be "control 'CODEOWNERS 1.0' contains 2 control rules. Control rule "'CODEOWNERS 1.1' requires a valid CODEOWNERS file must exist in the standard location." "Control rule 'CODEOWNERS 1.2' A CODEOWNERS file must contain a line setting '@${GITHUB_ORG}/security_champions' and '@${GITHUB_ORG}/application_security' as code owners for a repos `.wiz` file. A rule is the evaluation of a controls expected state against a resource type - this true false provides the simple effect of is the repo compliant to this control supplied by this policy by using ternary comparisons of all the rules to say if there are 4 control rules in the policy and all return true, then the repo is compliant to that control. Any of the 4 return false, then the repo is not complaint and that is tracked as such in the db.

By splitting the evaulation from the remediation it allows us to more easily scale and build this tooling out. It can let us do the simple thing of creating an evaluation github app that can be a read only app to eval the rpeo against its applied policy. Then the remediation github app is the write app and its used to write the PR to the repo with the remediations required for its complaince to become true.

The one part of this workflow that is nice is our evaluation is idompotent and always validated against the main branch of a repo at that eval run time. It always does the evaluation and updates the db of last eval and what its compliance is of what controls are passing and what are failing. This allows the ui to always be able to show the most up to date information as accurately adn quickly as possible. This split also means we can run a whole enterprise or specific orgs in that enterprise in different modes - evaluation or remediation. Evaluation is what i described above and is the default for repo guardian. Remediation is where after an evaluation a repo is marked for remediation if it fails a compliance control and there is a remediation for it. This also lets us run in eval mode to understand our compliance levels before turning on the rememdiations to be able to compare our policy and controls successes per repo or per org or enterprise.

Remediation is a workflow that takes a repo that is marked for remediation(a failed compliance rule with a remediation in its rule definition AND remediation is on for that repo via org or enterprise policy) and creates a PR in the repo with the fixes necessary to resolve those compliance failures. Because we will scope these remediations on a control like the "CODEOWNERS 1.0" which has 1 or more control rules in it, a remediation can be as precise as a single control rules remediation OR multiple control rules but to stay with our example scoped to the control rules for the "CODEOWNERS 1.0" control. Each control will get its own PR. This way if there is 1 or N number of control rules that need remediation they are all in a PR for the control(which makes sense more below when i describe how the code functions). When the remediation PR is created, it is then tracked in the database with things like the pr number, url, creation time/date, last reconciled(so last time the eval ran against this repo so we know if anything has changed in the eval - this allows us to skip a remediation if for any reason the scheduled reconcile comes around to run again against a repo with a remediation marker and an eval hasnt been done OR (THIS IS THE BIG PART) the evaluation hasnt changed. This means that remediations only run IF a evaluation change is made. What this means is that our evals of compliance are always evaluating the repos and tracking those compliance and policy posture facts. We only run a remediation IF there is a change in that compliance. So for onboarding a repo that fails all these rules will show a eval change/update since the eval runs against main and that repo is new with no files hence triggering a remediation with the remediation marker. The remediation runs, creates the prs it needs to and then updates its records with such - again so it is present in the ui. On the next eval of that repo, it again evals main and if it fails again the same compliance rules, it only updates the db with its last eval run time and doesnt change the remediation marker or what policies or controls are failing as those are still true. We will likely need some field on the repo in the db for this that signals to the remediation to look for first to eval if its going to run or skip like change_since_last_eval=true/false. So on the second eval run with no changes it flips that field to false as there were no changes and then the remediation marker stay so the remediation workflow then knows to look at this repo and check if that field on if it should run again.

Repo guardian has a policy type. That policy is a collection of controls. A policy can be applied on a repo level, org level, or enterprise level. It has the ability to say "these set of rules apply at an enterprise level, these set apply additionally to these orgs, and these set apply to these repos. It also has to negative to say ignore applying these rules or any rules at each of those layers as well. That gives us the ability to create a policy that can align to the whole enterprise and applied with excludes. Then each org can also have a policy IF needed to enable more controls or disable them or exclude specific repos in its org. Then inside that org policy can exist repo policy so a specific repo can enable or disable controls for just that repo. Effectively this is a simple check when a discovery is done to say "repo example/repo is part of org example which if not explicitly specified in the example org policy to exclude and if it doesnt have a repo policy specific to it will apply the controls from the enterprise policy and the example org policy". Now in our db per repo, we can see exactly what controls are applied, track their status, what policy they come from, along with our other normal data of last check, if there is an open pr with what controls waiting to be applied, how long its been open, etc. From that data we can query what repos are in compliance with the enterprise policy, org policy, etc to provide data to the ui to show what org is what percent compliant, where are they worst at, etc. My caveot here is we decide for or against the repo policy type and there is only an enterprise(which this is more or less the rquivilent to our default policy in the current version) policy and org policy. And in the enterprise/default policy this defines the controls to be checked in all orgs. This policy type has no excludes only what orgs are in its list of orgs. The org policy is where a control can be excluded for the whole org OR specified repos. It can also specify more controls than in the default policy and the simpliest way to see why this is important is say I have a test org and i created a new control and want everything on from the enterprise and in my test orgs policy I add this new control to be enabled to see how it will work or conflict or whatever.

A control rule is the opinionated definintion of posture. So an example control is "CODEOWNERS 1.0" which has control rules like "CODEOWNERS 1.1" and "CODEOWNERS 1.2" etc. Control will likely be an interface(maybe a base type idk) and then we will have a FileControl which either inherits or implements the Control type/interface. Control will likely have something like RunEval and RunRemediation as methods to implement or even just a Run interface that takes a run type of eval or remediation or if we want other stuff too. So with the codeowners example here, the eval is a file control type so it will need to have the ability to find, read, parse the expected file if it exists or doesnt. That way the code for any state the codeowners file is in is all contained within a package for codeowners. If the file doesnt exist, then the remediation can put the full file template there which satisfies all the control rules first for the PR without having to loop through all these rules individually like we do now. Flip side is the eval can parse the codeowners file and look for each specific control rule in that file that satisfies the control or fails it. The remediation then knows it only needs to create/update that file for the PR for that specific rule. It also means if it needs more than one those can all be templated at the same time.
