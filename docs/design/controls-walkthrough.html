Controls redesign walkthrough

An interactive tour of what DESIGN-0029 to DESIGN-0033 change in repo-guardian, why, what it costs, and what the adversarial review corrected.

Companion to controls-redesign.html (the full documents, deep dives and review). State of the designs as of 2026-10-03, including the review responses, which are the current position where they differ from the bodies. No network needed: every diagram on this page is built in the page itself.

Start here

repo-guardian today evaluates rules about paths and regexes, bundles every fix into one PR per repository, and runs one GitHub App that can both read and write. The redesign replaces that with controls: typed opinions ("a CODEOWNERS file that GitHub accepts and that gives security a say over .wiz"), assigned to repositories by a layered enterprise and org policy, evaluated by a read-only App, and remediated one PR per control by a second, write-capable App only when something actually changed.

The eight big changes

Each card states what changes, why, the alternative that was considered, and two complexity meters: how much it costs to build, and how much it costs to run. Click a card to flip it to the trade-off side.

What the adversarial review changed in this list. Four of the eight were reshaped by accepted findings: change detection gained epochs, revisions and an intent revision (AR-0030-03, AR-0029-04, AR-0032-10); PR handling gained slot reservation and compare-and-swap commits (AR-0032-05, AR-0032-07); posture now starts from assignments and keeps results through access loss (AR-0029-01, AR-0030-05); ownership split into Owns() and Reads() with canonical keys (AR-0030-02, AR-0031-02). The CODEOWNERS ordering was simply wrong and is reversed (AR-0031-01).

Change detection, live

This is the heart of change-driven remediation. One (repository, control) pair is shown. Press the buttons to make things happen in the world and watch which fields move and whether remediation becomes due. Nothing here polls: a PR is rebuilt only when one of these fields says so.

Fingerprint

sha256 over the control revision, every rule's status and every resource read's digest (blob SHA for files, canonical-JSON digest for API values). Excludes timestamps, evidence wording and the pinned commit, so an unrelated push is not a change.

Generations

eval_generation is bumped by evaluation when the fingerprint moves; remediated_generation is advanced only by remediation, after it acted. A new row starts at 1 > 0, so onboarding remediates by construction. No evaluation can erase a pending change.

Epoch, revision, intent

Epoch (assignment changed: version, mode, write set) fences stale runs. Revision (definition content digest) catches a template or evaluator change behind the same name@N. Intent revision catches an apply or eligibility change with no file drift.

    Setup impact

    What you add

    • A second task queue (repo-guardian-remediate) and a second worker Deployment (remediator), each scaled by KEDA on its own backlog. new
    • Two budget workflows per org instead of one, because each App installation has its own rate limit.
    • One short-lived workflow per failing control in remediate mode. Not permanent: it completes when the run records and nothing is due.
    • One schedule: remediation-sweep, hourly, as a backstop for lost signals and cleared holds.
    • A Temporal client in the api role for POST /repositories/{id}/evaluate, under its own mTLS identity. Signal-only by code, not by server policy (AR-0032-12).

    What you do not change

    • The namespace, the Temporal cluster (contrib chart 1.7.0), the CLI pin, mTLS, the OTel metrics handler.
    • The selector, coalescing, priority keys and ContinueAsNew pattern of the repository workflow.
    • TaskPriority (priority plus fairness by installation) on every activity and start.
    • Ingest: HMAC validation, 204 drops, REJECT_DUPLICATE starts, 503 on Temporal errors.

    Versioning and replay decided by AR-0029-03

    No GetVersion gates. The controls workflows get new type names and ids, so no Phase 10 to 13 history can replay into them. Cutover terminates the old executions after the writers stop. Replay tests and history capture apply to the new types from their first rc.

    Capacity you must size

    Activity concurrency per role (EVALUATOR_CONCURRENCY, REMEDIATOR_CONCURRENCY), rollout fan-out (POLICY_ROLLOUT_WINDOW), sweep batch sizes and per-role Postgres pools. Temporal, Postgres and egress are shared by both paths; only the GitHub budget, the key and the queue are isolated (AR-0029-05).

    Two roles, column grants

    Record-is-narrow is enforced by the database, not by prose: the evaluator and the remediator connect as different roles and each may write only its own columns. Toggle the role to see what it can do. The all topology connects as a member of both, which is why it is the weaker boundary (AR-0029-02).

    rg_evaluatorrg_remediatorall (member of both)

    Append-only tables (result_events, remediation_events, remediation_steps) revoke UPDATE and DELETE from both roles, as finding_events does today. Grant tests run as the two roles through pgtest.AppRole; a test as the owner proves nothing (AR-0032-09).

    Security boundary

    The private key is the boundary: a process that holds a write-capable App key can mint a write token whatever it intends. Toggle the topology to see which pods hold what. The guarantee is stated for split; all is a documented combined-trust topology for single-operator installs.

    Performance and scale

    Move the sliders to see what a fleet costs in GitHub calls, database rows and Temporal executions. Budgets use GitHub's documented App installation limits: 5,000 requests per hour, plus 50 per repository above 20, capped at 12,500. Two Apps means evaluation and remediation draw on separate budgets.

    What the design does to keep this cheap

    • One pinned, cached Reader per evaluation. Every control reads the same tree at the same SHA; a file read twice is fetched once.
    • Push rechecks are scoped to controls whose Owns() ∪ Reads() intersect the changed paths; unknown paths (2,048-commit cap, forced push) select all.
    • Remediation only on change. An unchanged fingerprint writes evaluated_at and nothing else; no signal is sent.
    • Resolution makes no API calls. It is a pure function of the snapshot and stored rows.
    • PR observation is one list call per evaluation, plus webhooks between schedules.

    What the review added, and its cost

    • Posture LEFT JOIN from assignments to results: the same row count, one more index, and a coverage number you did not have.
    • Slot reservation locks the repository's policy-state row for the duration of one insert; contention is per repository, not fleet-wide.
    • Update-branch before re-evaluating a PR head: one extra write call per stale PR, and a conflict is now a visible hold instead of a silently acknowledged PR.
    • A second discovery listing through the Remediation App for per-App access facts: one list call per installation per interval.
    • Journaled steps per remediation: a handful of small rows per run, which is what makes retries and recovery exact.

    Branching for parallel work

    • Contracts first, then fan out. Phase 0.5 is one commit: types, DDL, interfaces, OpenAPI stubs, reserved migration numbers 00004 to 00007.
    • Lanes own disjoint directories and merge in the order C (schema), A (framework), B (policy), D (API), so every merge compiles against merged code.
    • Shared files are pre-assigned: go.mod, names.go, openapi.yaml, values.yaml, CLAUDE.md, the one-line-per-type registry.
    • Two rc milestones: evaluate-only first, so posture can be compared with v1 before anything writes; then remediation.

    Where the review moved effort

    • Phase 0.5 grows: epoch, revision, Owns()/Reads(), Fixed/Manual/Blocked, canonical resource keys, the two App-access tables.
    • Phase 1 grows: a real CODEOWNERS matcher with GitHub's last-match-wins, tested against independent expected owners.
    • Phase 6 changes primitive: createCommitOnBranch with expectedHeadOid, slot reservation, step journal, update-branch, maintenance query.
    • Phase 3 grows: nullable event status, cascade deletes, the grant matrix as a test, remediation_due and remediation_maintenance as SQL.
