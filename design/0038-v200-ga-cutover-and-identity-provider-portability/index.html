    Overview

    The v2 line has shipped sixteen release candidates from the v2 branch and is running the controls model, remediation and the controls UI in the homelab. This design settles what has to happen for v2 to become main and ship v2.0.0: how the two branches converge, how the GA tag is produced so that a binary release, two registries and the chart all come out of one push, what the public docs site and the landing pages must say, and which of the IMPL-0030 soak gates still apply. It also closes the one operator-facing gap the audit found on the way: the API and UI are documented for Keycloak only, and three small assumptions in the code and the chart would trip an operator on Okta, Entra ID or Auth0. Part B makes the identity-provider contract explicit, adds the knobs those providers need, and ships recipes for each. Two further parts were added at review: Part C moves the public docs site off the drifted MkDocs copy onto a generator that renders what the docs actually contain (39 mermaid diagrams render as code today), and Part D evaluates the repository's supply-chain security (scanners, signing, SBOMs, provenance, pinning, branch rules) and tiers the gaps into what GA needs and what follows.

    The design is planning only. It produces four IMPLs: Part B (small, additive, shipped as an rc before GA), the GA cutover (Part A with Part D's first tier as a phase), the docs site (Part C, after GA), and supply-chain hardening (Part D's remaining tiers, after GA). See OQ1, OQ14 and OQ19.

    Goals and Non-Goals

    Goals

    • v2 becomes main through pull requests the main ruleset allows, with every rc tag still reachable and no history rewritten.
    • One v2.0.0 release: a signed goreleaser release, images on GHCR and ECR with SLSA provenance, the UI image, and the chart, all from one push to main, with jobs that visibly run (the June 2026 startup_failure post-mortem).
    • The public docs site publishes the v2 pages the moment main is v2; no page a new user reaches describes the v1 engine as current.
    • The soak gates IMPL-0030 set for GA are honoured, not re-derived.
    • An operator can run the API and UI against Okta, Entra ID or Auth0 from the docs alone, and the code and chart no longer assume Keycloak where they do today.
    • Every mechanical "v2 branch entry" (CI triggers, chart-testing target, CLAUDE.md rule 6) is listed with what changes at GA.
    • The public docs site is built from the same docs/ tree as TechDocs, renders mermaid, and is deployed from an Actions artefact rather than a long-lived gh-pages branch.
    • Every release artefact (binaries, two images, chart) carries a signature, provenance and an SBOM a consumer can verify from one documented page; the repository's scanners cover Go, TypeScript, containers, the chart and the workflows; and a red check blocks a merge.

    Non-Goals

    • An in-place upgrade from 1.x or from the pre-controls rcs. DESIGN-0032 D27 made 2.0 a fresh install; docs/operations/v2-migration.md is the runbook and this design only fixes its contradictions.
    • Supporting providers whose access tokens are not JWTs (Google) other than through a broker, or ID-token authentication at the API.
    • Nested group-claim paths (realm_access.roles); see OQ9.
    • IMPL-0026 (Temporal credential reload, OpenBao certificates) and DESIGN-0034 (CODEOWNERS ownership) stay post-GA, as IMPL-0030 recorded.
    • A Go module path change to /v2; see OQ11.
    • Changing the authorization model (groups → orgs, defaultOrgs, clients). It is provider-neutral already; only the claim it reads the client from is made configurable.

    What the readiness audit found

    A read-only audit of the tree on 2026-10-24 found four things that would break or mislead if v2 were flipped today, plus a set of smaller items. In order of blast radius:

    1. No workflow produces the v2.0.0 binary release as planned. release.yml runs goreleaser only off the semver bump; with dont-release the bump is skipped, the release job is skipped, and publish-ghcr/publish-ecr run with an empty tag, so their image jobs are gated off. prerelease.yml matches v*-* only. The only workflow a hand-pushed v2.0.0 tag triggers is changelog-update.yml.
    2. The public docs site would publish v1. gh-pages.yml deploys mkdocs-ghpages.yml on every push to main. That file's nav has Getting Started and Policy Reference under Usage, DESIGN/IMPL entries up to 0009 and no Operations section; none of controls-reference, ui, api, v2-* is in it. mkdocs.yml (the TechDocs config) has them all.
    3. The landing pages describe v1. README.md, docs/index.md, docs/usage/getting-started.md, docs/ADDING_RULES.md, docs/operations/{aws,scaling,ent-setup}.md and the chart README's introduction still describe reconcilers, guardian.hcl, Valkey, watch = true and chart values the 2.x chart fails the render on.
    4. v2-migration.md contradicts itself on RECONCILE_FRESHNESS (read by migrate at line 225; "none" at 271) and migrate.freshness (a replacement at 236; removed at 295).

    Smaller: changelog-update.yml does a full git-cliff regeneration on the tag push, which IMPL-0029 9.5 noted would drop the hand-written 1.x entries; the UI changelog gate needs a 2.0.0 entry beside the chart bump; IMPL-0028 is Draft with every task ticked, IMPL-0025's body says Draft while its frontmatter says Completed, DESIGN-0036 is Approved; #232 and #235 are fixed in code but open; the deploy/MIGRATED.md tombstone is due 2026-11-30; two Dependabot alerts on main are already fixed on v2.

    How the API and UI authenticate today

    DESIGN-0027 specified a provider-neutral contract: the API takes an OIDC access token for its audience, reads a name claim and a groups claim, and maps groups to orgs in a YAML file. The implementation is faithful to that:

    • internal/api/authn.go: go-oidc discovery, RS256/ES256 only, iss equal to OIDC_ISSUER, aud containing OIDC_AUDIENCE (string or array), 60s skew on exp/nbf, refuses tokens carrying nonce, at_hash or typ: ID, then reads OIDC_NAME_CLAIM (default preferred_username) and OIDC_GROUPS_CLAIM (default groups) as top-level keys. Claims.Client is read from azp and nothing else.
    • internal/api/authz.go: groups → orgs, defaultOrgs, and clients keyed on that azp for IdPs that put no groups on client-credentials tokens (DESIGN-0027 OQ22).
    • ui/server/: authorization code + PKCE S256 with state and nonce, scopes from OIDC_SCOPES (code default openid profile email offline_access), token endpoint authentication hard-coded to client_secret_post, no audience/resource parameter, access token forwarded to the API, refresh within 60s of expiry, RP-initiated logout when discovery advertises end_session_endpoint, revocation when it advertises revocation_endpoint.
    • Chart: api.auth.{issuer,audience,nameClaim,groupsClaim}, api.authz.*, ui.oidc.{clientId,scopes} with the scopes default [openid, profile, groups, offline_access] (which differs from the code default), ui.existingSecret. The UI's issuer is api.auth.issuer. values.schema.json declares api.auth.enabled, issuer, audience only.
    • Docs: the authentication rules in docs/usage/api.md are neutral; the only setup walkthrough is "Keycloak example", and docs/usage/ui.md points at it. Okta and Entra appear only in DESIGN-0027's diagram and in the Temporal client-credentials discussion (DESIGN-0028, INV-0020).

    So the code is close to neutral. What would stop an Okta operator is a clients block that silently does nothing (Okta issues cid, not azp), an app that has to be switched to client_secret_post, a chart scope default (groups) that Okta's custom authorization servers reject as undefined, and no page telling them any of that. Auth0 adds one more: without an audience parameter it returns an opaque access token, which the API refuses as malformed. Google's access tokens are always opaque, so Google only works behind a broker.

    Detailed Design

    Part A: the GA cutover

    A1 Branch convergence

    Two merges, both merge commits, both through pull requests:

    gitGraph
  commit id: "5bd96bb (merge-base)"
  branch v2
  checkout main
  commit id: "#203 rgctl"
  commit id: "#227 #225 #228 #229"
  checkout v2
  commit id: "rc.12 … rc.15"
  commit id: "517f0cd rc.16" tag: "v2.0.0-rc.16"
  merge main id: "M1: main → v2 (sync PR)"
  commit id: "IMPL identity providers (rc.17)" tag: "v2.0.0-rc.17"
  commit id: "GA prep: chart 2.0.0, docs, reverts"
  checkout main
  merge v2 id: "M2: v2 → main (merge commit, labelled)" tag: "v2.0.0"

    M1, main into v2. A sync PR against v2 that brings rgctl, the rgctl runbook and the base-branch: true guard. Conflicts are expected only in release.yml (keep the guard) and go.mod/go.sum (keep v2's newer versions). After M1, v2 is a superset of main and the final merge is conflict-free by construction.

    M2, v2 into main. A PR against main, merged with the merge commit method. Squash would collapse the whole v2 history into one commit and leave every rc tag pointing at commits no longer reachable from main; rebase would rewrite them. A merge commit keeps the rc tags reachable, which A2 depends on, and keeps git log main honest about what shipped in each rc. The repository's default merge method for feature PRs is squash; M2 is the one PR where the maintainer picks "Create a merge commit" by hand (D1).

    Everything that must be true of main at GA (chart 2.0.0, the docs rewrite, the branch-entry reverts, the 2.0.0 changelog entry) lands on v2 before M2, in the GA-prep PR, so that M2 carries a tree that is already GA-shaped and the push to main can be the release.

    A2 The release mechanism

    The pipeline on main is release.yml: bump-version (jefflinse/pr-semver-bump, mode bump) reads the merged PR's labels, tags, and hands the tag to release (goreleaser) and to ghcr.yml / ecr.yml (image, UI image, chart, three SLSA jobs each). The action chooses the version to bump from by parsing every tag as semver (loose, so pre-releases parse), sorting descending, and with base-branch: true taking the newest one whose commit is reachable from the base branch; annotated tags are dereferenced.

    After M2, the newest tag reachable from main is v2.0.0-rc.16 (or rc.17, see A1), because the rc tags point at v2 commits that the merge commit makes reachable. node-semver's increment rules for a pre-release of 2.0.0 are:

    Label on the merge PR semver.inc("2.0.0-rc.N", …)
    major 2.0.0
    minor 2.0.0
    patch 2.0.0

    So a labelled M2 produces exactly v2.0.0, and the whole pipeline designed for 1.x releases runs: goreleaser builds and signs the binaries and creates the GitHub release; ghcr.yml and ecr.yml receive tag: v2.0.0, build and push both images with latest and 2.0 tags (!contains(tag, '-')), publish the chart, and attach SLSA provenance to all three. Nothing is pushed by hand.

    This revises IMPL-0030 OQ12(a) (dont-release + hand tag), which would have left release skipped and both image jobs gated off; the hand tag would have triggered only changelog-update.yml. The label is major (OQ2), because that is what the release is, and because major is the only label whose semantics survive if the rc tags were ever unreachable (a minor or patch from 1.14.1 would cut 1.15.0 or 1.14.2, silently, from v2 code). The pre-merge checklist therefore includes: git tag --merged <M2 head> shows v2.0.0-rc.16; no v2.0.0 tag or release exists; release.yml on the merge head has base-branch: true; the PR carries exactly one semver label.

    sequenceDiagram
  participant PR as M2 merge (label: major)
  participant R as release.yml
  participant B as bump-version
  participant G as goreleaser
  participant P as ghcr.yml / ecr.yml
  PR->>R: push to main
  R->>B: pr-semver-bump (base-branch: true)
  B-->>B: newest reachable tag = v2.0.0-rc.N
  B-->>R: tag v2.0.0
  R->>G: release --clean @ v2.0.0 (GPG-signed)
  R->>P: tag=v2.0.0
  P-->>P: image, ui-image, chart + SLSA ×3; latest & 2.0 tags
  P-->>R: digests

    Two guards from the release post-mortem carry over unchanged: confirm the push-triggered run creates jobs (a startup_failure has none and is only visible on the run's web page), and read digests from the expression layer, never from a shell-inlined metadata blob.

    prerelease.yml keeps working for future vX.Y.Z-rc.N tags on main: the v*-* filter does not match v2.0.0 and the file is harmless on main. Its comment ("lives on v2 until v2.0.0") is updated (A6).

    B3 Code changes

    B3.1 The client claim (internal/api). AuthnConfig gains ClientClaim string; config/api.go reads OIDC_CLIENT_CLAIM (default azp); verify sets Claims.Client from all[a.cfg.ClientClaim] via stringClaim instead of the typed AZP field, which is removed from tokenClaims. The chart exposes it as api.auth.clientClaim. The existing clients semantics and the "never map the UI's client ID" warning are unchanged; the warning is generalised to "whatever claim names the client, every user token from the UI carries the UI's client in it". A single configured name is chosen over an ordered fallback list (azp, client_id, cid, appid) because it matches nameClaim/groupsClaim, is explicit in the authz file's threat model, and cannot surprise an operator whose provider emits two of those claims with different values (OQ4).

    B3.2 The ID-token check. isIDToken is unchanged in behaviour; its comment and the api.md bullet stop naming Keycloak: "a typ claim of ID, which some providers put in the payload".

    B3.3 Token endpoint authentication (ui/server). OIDC_TOKEN_AUTH_METHOD with values client_secret_post (default, today's behaviour) and client_secret_basic; oidc.ts picks client.ClientSecretPost or client.ClientSecretBasic accordingly. Config validation rejects anything else. The default stays post so rc deployments do not change behaviour on upgrade (OQ5).

    B3.4 Extra authorization parameters (ui/server). OIDC_AUTHORIZATION_PARAMS, a JSON object of string → string, merged into buildAuthorizationUrl's parameters after the fixed ones (redirect_uri, scope, code_challenge*, state, nonce), which cannot be overridden: validation refuses those keys. Chart value ui.oidc.authorizationParams: {}. This covers Auth0's audience, RFC 8707 resource, Entra's domain_hint/prompt, and anything a future provider wants, without a knob per parameter (OQ6).

    B3.5 Scopes. No code change; defaultScopes in config.ts stays openid profile email offline_access. The chart default moves to match it (B4).

    B3.6 Test fixtures. internal/api/oidctest gains token shapes for Okta (cid, scp, uid, no azp, aud as a string), Entra (roles, GUID groups, appid), and a namespaced groups claim (https://example.com/groups); TestAuthn_* table cases drive each through verify with the matching ClientClaim/GroupsClaim and assert Claims.Client and Claims.Groups. The e2e mock issuer keeps its Keycloak-shaped token and gains a TOKEN_AUTH=basic option so the client_secret_basic path has one end-to-end run.

    B5 Provider recipes

    Each recipe in identity-provider.md has the same five headings (issuer and audience, UI client, groups, machine clients, chart values) so an operator can diff them. The content, as the audit established it:

    Keycloak (moved from api.md, unchanged): API client as audience, UI confidential client with PKCE and the two redirect URIs, Audience mapper, Group Membership mapper with full path off, service-account clients mapped by azp. Issuer https://<host>/realms/<realm>.

    Okta: a custom authorization server (API Access Management) is required; tokens from the org authorization server cannot be validated by third parties. Issuer https://<org>.okta.com/oauth2/<server id>, audience the server's audience (api://default or a chosen one). Add a groups claim to access tokens on that server (filter by group); group names are the api.authz.groups keys. Machine clients: api.auth.clientClaim: cid, or a groups claim on client-credentials tokens.

    Entra ID: app registrations for the API (expose a scope, set accessTokenAcceptedVersion: 2 so iss matches the v2 discovery document) and the UI (web platform, redirect URIs, client secret). Issuer https://login.microsoftonline.com/<tenant>/v2.0, audience the API app's client ID (or api://<id>). Put the API scope in ui.oidc.scopes so the access token is for the API. Many groups inflate three tokens in the session cookie; the ten-chunk limit in session.ts is the ceiling and is documented, not raised.

    Auth0: issuer https://<tenant>.<region>.auth0.com/ (trailing slash), an API registered with an identifier that becomes the audience, ui.oidc.authorizationParams: {audience: <identifier>} so the access token is a JWT, a post-login Action adding a namespaced groups claim (https://example.com/groups) set as groupsClaim, RP-initiated logout enabled on the tenant for end_session_endpoint, offline_access enabled on the API.     Google: not supported directly; its access tokens are opaque. Use a broker (Keycloak, Dex, Auth0, Okta) federating to Google and follow that broker's recipe.

    Decisions

    • D1 Merge commits for both convergence merges. Squash or rebase would orphan the rc tags that A2's bump depends on and rewrite the history the rc releases point at.
    • D2 One mkdocs nav. mkdocs-ghpages.yml inherits mkdocs.yml; docz keeps the nav current for both sites.
    • D3 Prepend, never regenerate, the root changelog. The 1.x entries are hand-curated and the tag workflow must not be able to drop them.
    • D4 A provider-neutral contract page with per-provider recipes. The code is neutral; the docs must be too, and the recipes carry the product-specific steps rather than the code growing a provider switch.
    • D5 One configured claim name per role, not fallback lists. The client claim joins nameClaim/groupsClaim as an explicit setting so the authz file's trust boundary is readable from the values.
    • D6 Defaults do not move behaviour on upgrade, except the chart scopes. tokenAuthMethod defaults to today's post; the scopes default aligns with the code because the chart value was the outlier and the Keycloak recipe does not need groups.
    • D7 A generic authorizationParams map instead of an audience knob. Reserved keys are refused so the map cannot break PKCE or state.
    • D8 docs/ stays the single source for TechDocs and the public site. No markdown moves; the generator reads the tree in place. TechDocs is MkDocs and keeps mkdocs.yml.
    • D9 The public site deploys from an Actions artefact, not a branch. The gh-pages branch goes once the Actions deploy serves.
    • D10 Every published artefact gets an SBOM attestation and an in-workflow verify before anything else in Part D, because they are the two things a consumer cannot add after the fact.
    • D11 Rulesets require checks, not signatures, at GA. Merge commits are required (D1), so linear history stays off; required signatures wait for a decision on bot commits (OQ17).
    • D12 Renovate owns version updates; Dependabot owns security updates. One tool per job ends the duplicate PRs.

    Testing Strategy

    Part B, unit. internal/api: table tests over oidctest shapes for Keycloak, Okta, Entra and a namespaced groups claim, asserting Claims.Client, Claims.Groups, Claims.Name and the refusal reasons; a case with ClientClaim: cid on a Keycloak-shaped token yields an empty client (and so clients grants nothing), which is the property the authz warning relies on. ui/server: config tests for OIDC_TOKEN_AUTH_METHOD values and OIDC_AUTHORIZATION_PARAMS parsing and reserved-key refusal; auth.ts test that the authorize URL carries the extra parameters and that the fixed ones win.

    Part B, chart. helm-unittest: each new value → env var; the reserved-key refusal; OIDC_SCOPES default string; the schema rejecting an unknown tokenAuthMethod.

    Part B, e2e. The mock issuer runs once per Playwright project; the no-remediation project is switched to client_secret_basic so both methods have a run without a third stack.

    Part A, pre-merge checks (scripted in the GA IMPL, run by the maintainer): git merge-base --is-ancestor origin/main v2 after M1; git tag --merged on the M2 head lists v2.0.0-rc.16; no v2.0.0 ref; release.yml has base-branch: true; mkdocs build --strict --config-file mkdocs-ghpages.yml passes; make lint-ui passes with the 2.0.0 entry; grep -rn 'guardian.hcl\|watch = true\|Valkey' README.md docs/index.md docs/usage/getting-started.md is empty.

    Part C. make lint-docs builds site/ strictly with the links validator; a CI job on the docs paths filter runs it on pull requests; one Playwright smoke in the UI's pinned image loads the built site's home, a design page with a mermaid diagram (asserting an <svg> in the diagram container) and a search result. The Pages deploy job runs only on main.

    Part D. Each scanner job is proven non-vacuous once in its PR by pointing it at a known-bad fixture (an unpinned action for actionlint, a latest base image for trivy config, a CVE-bearing test dependency for bun audit) and watching it fail, then reverting. SBOM presence is asserted in ghcr.yml by cosign verify-attestation --type spdxjson on the just-pushed digest, which is also the verify-after-sign step. The rulesets are checked by opening a PR with a deliberately failing required check and confirming the merge button is blocked.

    Part A, post-merge checks: the release.yml run on the merge commit has jobs; the bump-version log says "Only considering tags on branch main" and tags v2.0.0; goreleaser's release exists and is signed; cosign verify on both images; chart helm pull --version 2.0.0; latest resolves to the 2.0.0 digest; the Pages deploy renders the v2 nav.

    5. M2: PR v2 → main, label major, merge commit. The push produces v2.0.0, the binaries, both registries, the chart and the docs site. Post-merge checks (Testing Strategy).
