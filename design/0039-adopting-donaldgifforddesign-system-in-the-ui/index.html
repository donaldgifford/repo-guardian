    Overview

    The UI stops keeping its own copy of the design. ui/web installs @donaldgifford/design-system 0.3.0, takes its stylesheet, tokens, primitives, blocks and shell from it, and deletes components/ui, components/charts, the local shell chrome, the @theme in index.css and the radix-ui dependency. What stays in this repository is what knows about repositories, controls, findings and remediations.

    INV-0025 established that this is possible and what it costs. This document decides how it is done: where the package sits in the build, how every install path gets its token, what each local file becomes, what the app looks like afterwards, and the order of the work.

    Goals and Non-Goals

    Goals

    • ui/web/src holds no local copy of anything the package provides. radix-ui, recharts, clsx, tailwind-merge, class-variance-authority and the two @fontsource packages leave ui/package.json.
    • No utility class or var() reads an old token name (panel, panel-2, ok, warn, bad, or accent meaning the blue).
    • The package is pinned exactly and installs on a laptop, in CI, in the image build and for Renovate, with the token never written to a file or an image layer.
    • Behaviour that users and tests rely on is kept: every route and URL parameter, the drawer's ?open=, dialog and table names, CSV file names, the saved time-zone choice, keyboard operation, and the axe suite passing unchanged.
    • The differences in look are the ones listed in this document and no others.
    • A problem found in the package becomes an issue on donaldgifford/design-system, not a patch here.

    Non-Goals

    • No API, BFF, chart or Go change. ui/server is untouched.
    • No new page, panel, filter or column, and no change to what any page shows.
    • No light theme (OQ2): the app stays dark only.
    • No change to the icon set (INV-0024) or to the Icon component.
    • No change to the routes' search parsing. The lists do not adopt the package's listSearchSchema or page-number paging.
    • No Storybook in this repository. The package's is the catalog.
    • No vendoring or forking of the package.

    Background

    DESIGN-0036 gave the v2 UI its design language: one dark theme declared in index.css, shadcn-style primitives hand-copied into components/ui, and chart components over Recharts. DESIGN-0037 added the controls pages on top. The primitives were kept free of domain knowledge on purpose, and @donaldgifford/design-system 0.1.0 was made by backporting them and rebuilding them on Base UI. Issue #252 asks this repository to consume that package instead of its own copy.

    INV-0025 compared the two, sent 29 gaps and 22 differences upstream (design-system#11), and tested an install. Its results are the premises here:

    • With 0.3.0 nothing blocks the migration. Every gap was either fixed in the package or decided as "stays local".
    • The package installs from GitHub Packages, typechecks under this repository's compiler flags, builds, passes check:dist and builds in Docker with a build secret.
    • Upstream's rule is that a gap or bug is fixed in the package and a design difference is the package's design. Two differences are therefore accepted and change how the app looks: the shell and the dark destructive red.
    • Six things stay local by upstream's decision: DeltaText, a card wrapper with the title/subtitle/right API, popover option rows, the ErrorBoundary, inline Loading/Empty, and the options-driven tabs with their URL binding.

    What the package is, in one paragraph: React 19, Tailwind v4 with the theme in CSS, shadcn components on Base UI, Tabler icons, Recharts and TanStack Table. It publishes TypeScript and CSS source with no build step, so this app's Vite, Tailwind and tsc compile and check it. It is imported per module (/components/<name>, /blocks/<name>, /shell/<name>, /lib/<name>, /hooks/<name>, /globals.css), with no barrel. It is 0.x: a minor release may break.

    Rules that keep this shape:

    • One direction. Local code imports the package; nothing local is imported by a package path alias, and no file re-exports package modules as a local barrel. A call site imports @donaldgifford/design-system/blocks/meter, not a local meter.
    • components/ui and components/charts cease to exist. A local component that survives lives directly under components/ and has a domain or app reason to exist, written in its header comment.
    • No styling of package internals. Local code passes className and props. It does not target a package component's data-slot in CSS to restyle it; a look that cannot be reached with props is an upstream issue.
    • An ESLint rule keeps Radix out. no-restricted-imports bans radix-ui and @radix-ui/* in ui/web, beside the existing HTML sink ban, so a copied snippet cannot bring it back. (cmdk still pulls a Radix dialog package in transitively; that is the package's dependency, not ours.)

    2. Dependency and install

    ui/package.json:

    Change Entry
    add, devDependencies, exact "@donaldgifford/design-system": "0.3.0"
    remove once unused radix-ui, recharts, clsx, tailwind-merge, class-variance-authority, @fontsource/ibm-plex-sans, @fontsource/jetbrains-mono
    keep @tabler/icons-react (the local Icon), react, react-dom, tailwindcss, @tailwindcss/vite

    It is a dev dependency because Vite compiles it into the bundle and the BFF never imports it. That is what lets the image's production-install stage run with no token (INV-0025 F8). recharts goes because once components/charts is deleted nothing here imports it, and keeping our 3.10.1 beside the package's pinned 3.8.0 bundles the library twice.

    ui/.npmrc, committed, holds no secret:

    @donaldgifford:registry=https://npm.pkg.github.com/
//npm.pkg.github.com/:_authToken=${NPM_TOKEN}

    Path Change
    Laptop make ui-install uses NPM_TOKEN from the environment and, when it is unset, gh auth token (OQ5). ui/README.md documents the read:packages scope.
    ci.yml ui, ui-e2e Each job gains permissions: { contents: read, packages: read } and env: NPM_TOKEN: ${{ secrets.GITHUB_TOKEN }} on the install step. The workflow default stays contents: read.
    ui/Dockerfile Build stage: COPY package.json bun.lock .npmrc ./ and RUN --mount=type=secret,id=NPM_TOKEN NPM_TOKEN="$(cat /run/secrets/NPM_TOKEN)" bun install --frozen-lockfile. The deps stage is unchanged. The secret is read from its mounted file because the pinned Dockerfile syntax (1.7) has no env= on a secret mount.
    docker-bake.hcl _ui gains secret = ["id=NPM_TOKEN,env=NPM_TOKEN"], inherited by ui-dev, ui-ci and ui-release.
    Makefile docker-build-ui Passes NPM_TOKEN the same way as ui-install.
    ghcr.yml ui-image The bake step gets env: NPM_TOKEN: ${{ secrets.GITHUB_TOKEN }}. The job already holds packages: write. No change to ui-image-slsa, and none to release.yml's permission ceiling.
    Renovate A host rule for npm.pkg.github.com in renovate.json5, reading a Renovate secret, and :node added to extends. It moves to the shared preset when renovate-config#18 lands (OQ6).
    Dependabot The bun entry for /ui gets a registries reference, or its security updates for /ui cannot resolve the lockfile (OQ6).

    Three things the release post-mortems make non-negotiable here:

    • The token reaches bun only through the environment or a secret mount, never inlined into a run: script from an expression other than secrets.*.
    • After the ghcr.yml edit, the ui-image job is proved before merge with a workflow_dispatch of ghcr.yml on the branch with dry_run: true, and the first push-triggered release.yml run after merge is checked to have created jobs. A green PR does not exercise this path.
    • ghcr.yml and ecr.yml are diffed after the edit. ecr.yml builds no UI image today, so it should not change.

    3. Stylesheet and tokens

    ui/web/src/index.css shrinks to the import and the one thing the package cannot know:

    @import "@donaldgifford/design-system/globals.css";

    ui/web/index.html gets <html lang="en" class="dark">, because the package's :root is the light theme and .dark selects ours. The five @fontsource imports leave main.tsx; globals.css imports the same faces.

    What happens to each block of today's index.css:

    Block Fate
    @import "tailwindcss" from globals.css
    @theme colours deleted; the package's semantic tokens replace them
    --breakpoint-nav (900px) deleted with the local sidebar; the package shell collapses at 768px
    --radius-*, --font-* deleted; same values in the package
    :root { color-scheme: dark }, body deleted; in the package's base layer
    :focus-visible outline deleted; the package has the same rule on --ring
    prefers-reduced-motion block deleted; in globals.css since 0.2.0
    rg-* keyframes, animate-* utilities deleted; overlays animate through tw-animate-css in the package

    Token names:

    Here today After Notes
    panel card
    panel-2 muted as a hover or recessed surface; see accent
    ok / warn / bad success / warning / destructive utilities, var(--color-*) and the Tone type in lib/format.ts
    accent (the blue) primary focus rings read ring
    info, avatar, background, foreground, muted-foreground, border unchanged

    accent is the one name that cannot be renamed blindly: in the package accent is a hover surface. All 40 uses are classified by this rule before any edit:

    The use is Becomes
    text, icon, link or chart stroke in the brand blue primary
    a focus ring or outline ring
    a selected row or pill tint (bg-accent/12) primary at the same opacity
    a hover or pressed surface accent (the package's meaning)

    After the rename, a check in make lint-ui greps ui/web/src for the old names (-panel, -ok, -warn, -bad, --color-panel, --color-ok, --color-warn, --color-bad) and fails on a hit, so a later change cannot reintroduce a class that silently generates nothing. accent cannot be checked this way and is covered by review and the visual baselines.

    Chart colours follow the same rule: posture and bucket colours that mean a status read --success/--warning/--destructive/--info; series colours with no meaning read --chart-1 to --chart-5.

    Composition, all from package parts:

    Region Built from Content
    Frame SidebarProvider, SidebarInset the provider is controlled; the collapsed state is the app's (OQ3)

    Consequences that are behaviour, not look:

    • The breadcrumbs move into the top bar. They stay one nav named "Breadcrumb" with the leaf marked aria-current="page", built on the package's Breadcrumb parts with BreadcrumbLink render={<Link/>}. crumbsFor, CrumbLabelProvider and useCrumbLabel are unchanged.
    • Sign out stays a POST form submitted from the menu item, so the BFF's Origin check holds. The item uses onClick: a Base UI menu item has no onSelect, and one left in place never fires.
    • The menu label sits inside a DropdownMenuGroup, which Base UI requires.
    • The reserved data-slot="app-switcher" element goes. The sidebar header is where a portal's switcher would attach.
    • ⌘K and the sidebar's ⌘B are both bound; the palette keeps ⌘K.
    • Below 768px the sidebar is a sheet opened by the same SidebarTrigger; MobileSidebar and its state in Shell go.
    • Shell still asks /me first and renders AccessView for a caller with no visible org, outside the frame.

    CommandPalette keeps its data and matching and is rebuilt on CommandDialog with commandProps={{ shouldFilter: false, loop: true }}, CommandInput, CommandGroup and CommandItem.

    5. Component dispositions

    Every local file has one of four fates: replace (call sites import the package module), rebuild (the file stays, rewritten on package parts), keep, or delete.

    Primitives and overlays:

    Local Fate Becomes
    ui/avatar replace components/avatar; the menu uses AvatarMark
    ui/badge replace components/badge with variant; Tone in lib/format.ts takes the package's names
    ui/button replace components/button; the three calls with no variant get variant="outline"; <Link><Button tabIndex={-1}> nestings become render={<Link/>}
    ui/card rebuild components/Panel.tsx: the title/subtitle/right/bodyClassName API on Card render={<section/>} and CardTitle render as an h3
    ui/tabs rebuild components/SegmentedTabs.tsx: Tabs({label, options, value, onChange}) and SearchTabs on the package's Tabs/TabsList/TabsTrigger
    ui/table delete unused today

    Rules for the migration's own tests:

    • A stage is green before the next starts. make lint-ui, make test-ui and make test-ui-e2e pass at the end of every stage in the rollout below, so a regression is attributed to one stage.
    • The visual baselines move twice at most: once after the token swap if the colour shift exceeds the comparison threshold, and once after the shell. Any other stage that changes a screenshot has changed the look by accident and is fixed, not re-baselined.
    • A rewritten test is shown to fail first. For each e2e assertion whose selector changes, the new selector is run against the old build or with the behaviour removed, so a selector that matches nothing cannot pass as a kept guarantee.
    • Keyboard checks are explicit, because Base UI replaces every overlay: focus lands inside each overlay on open, returns to the row or trigger on close, Escape closes, and the row is activatable with Enter and Space. These exist in ui.spec.ts and behaviour.test.tsx today and are kept as behaviours.

    How it ships:

    • One implementation plan, one pull request, with the stages as its phases (OQ8). The intermediate states exist as commits, not as releases.
    • The pull request carries a semver label, so merging it cuts a release (OQ9), with a ui/CHANGELOG.yaml entry and the chart appVersion bump in the same change.
    • Rollback is a revert of the merge. Nothing persistent changes: the one new browser storage key is ignored by the old build.
    • The package is pinned exactly. A later update is a Renovate pull request that runs the whole suite including the visual comparison, because a 0.x minor may change look or API.

    Documents updated in the same change: CLAUDE.md (§The UI: the package, the token, the local survivors, the dom preload), ui/README.md (setup and the token section), DESIGN-0036 (a note that its token and shell sections are superseded by this design). The mockup (ui/design/repo-guardian-mockup.html) is already redrawn in this design's pull request: its :root values are the package's dark theme and its frame is the package shell (OQ1).

    Risks:

    Risk Handling
    GITHUB_TOKEN cannot read another repository's package in CI, or in a pull request from a fork proved in stage 1 before anything depends on it; the fallback is a repository secret holding a read:packages token
    The release pipeline fails silently after the ghcr.yml edit dry-run dispatch before merge; check the first push-triggered run creates jobs
    A 0.x release breaks the app exact pin; updates only through a reviewed pull request with the full suite
    A gap appears mid-migration an upstream issue; the stage waits or the local file stays one more stage. No local patch of package internals
    Bundle growth measured at stage 7 against main (989 kB JS, 31 kB CSS); the spike's 1,761 kB was every module with nothing deleted
    The package registry is unreachable installs fail closed; the lockfile and Bun's cache cover CI reruns only partly. Accepted: the same holds for npm

    Open Questions

    All nine were decided on 2026-11-17; each decision is recorded under its question. Option (a) was the recommendation in each.

    OQ1: What happens to the mockup?

    ui/design/repo-guardian-mockup.html is the UI's reference and carries its own copy of the tokens and the shell. The standing rule is that a UI design is accepted together with its mockup. It has not been edited yet, pending this answer.

    • (a) ✅ recommended: update the mockup in this design's pull request, limited to the frame (the package shell) and the token values, and keep it as the reference for page composition. Follows the standing rule; the pages are the part Storybook does not show.
    • (b) Retire the mockup. The package's Storybook is the reference for components and shell, the running app for pages. Removes a second hand-kept copy of the design, which is what this migration is for, but leaves no place to draw a page before building it.
    • (c) Freeze it with a banner saying the frame and tokens are out of date. Cheapest, and leaves a reference known to be wrong.
    • other:

    Decision: (a), 2026-11-17. The mockup's frame and token values are redrawn in this design's pull request; it stays the reference for page composition.

    OQ2: Does the app offer the light theme?

    The package ships both themes; the app is dark-only today.

    • (a) ✅ recommended: dark only, class="dark" fixed on <html>. Keeps this change a migration; a light theme doubles the visual baselines and needs every status colour and chart checked.
    • (b) Add a theme toggle with a stored choice in this work. The package makes it cheap to switch, but not to verify.
    • (c) Follow the operating system's preference with no toggle. Changes what many users see on the day of the upgrade.
    • other:

    Decision: (a), 2026-11-17. Dark only.

    OQ3: Is the sidebar's collapsed state remembered?

    The package's provider is controlled and leaves persistence to the app.

    • (a) ✅ recommended: remember it in localStorage under rg.sidebar, beside rg.tz. A user who collapses it expects it to stay collapsed.
    • (b) Do not remember it; it opens expanded on every load. No new storage key, at the cost of the preference.
    • (c) Keep it in the URL. Shareable, but it is a personal preference and would ride along in every copied link.
    • other:

    Decision: (a), 2026-11-17. localStorage key rg.sidebar.

    OQ4: What is the sidebar's header?

    The package's ShellSidebarIdentity always draws the up-down chevrons of a menu, and there is no second app to switch to.

    • (a) ✅ recommended: a link to / built from SidebarMenuButton and AppMark with the title and subtitle, without ShellSidebarIdentity, so no chevron promises a menu that is not there.
    • (b) Use ShellSidebarIdentity in a menu with one entry, as the package's story does. Matches the catalog exactly and shows a menu with nothing to choose.
    • (c) Ask upstream for an identity without the chevron and wait for it. The cleanest result, and it blocks the shell stage on a release.
    • other:

    Decision: (a), 2026-11-17. A link to / with the mark, title and subtitle, and no menu chevron.

    OQ5: How does a developer's install get the token?

    • (a) ✅ recommended: make ui-install and make docker-build-ui use NPM_TOKEN when set and otherwise gh auth token. One less setup step for anyone already using gh; CI always sets the variable, so the fallback never runs there.
    • (b) Require NPM_TOKEN to be exported, and fail with a message naming the README section. Explicit, and one more thing to set up.
    • (c) Read it from a mise environment file kept out of git. Automatic once set, and puts a token in a file on disk.
    • other:

    Decision: (a), 2026-11-17. NPM_TOKEN when set, otherwise gh auth token.

    OQ6: How do Renovate and Dependabot reach the package?

    Both need a token for npm.pkg.github.com, and both take it from a secret only a maintainer can set. Without it, Renovate does not see new versions and Dependabot's security updates for /ui may fail to resolve the lockfile.

    • (a) ✅ recommended: add a Renovate hostRules entry in renovate.json5 and a Dependabot registries entry, each reading a secret the maintainer creates (a read:packages token). The tasks are marked "deferred - human required"; until then the pin is bumped by hand.
    • (b) Put the host rule in the shared donaldgifford/renovate-config preset, since every consumer of the package needs it. Right place in the long run, a change in another repository now.
    • (c) Configure neither; bump the package by hand and accept that Dependabot's /ui security updates may fail. No secret to manage, and a 0.x dependency that silently goes stale.
    • other:

    Decision: (a) now, and (b) as the destination, 2026-11-17. This repository adds its own host rule and Dependabot registry entry, both reading a maintainer-created secret. The shared preset is requested in renovate-config#18, because other apps will consume the package; when it lands, renovate.json5 here extends it and drops its own host rule.

    OQ7: Do the embedded tables get a header sort?

    The package's plain table sorts on a header click. Today no table here does.

    • (a) ✅ recommended: off for now (sorting disabled on embedded tables' columns). Keeps the change a migration and keeps orders that mean something, such as worst controls first.
    • (b) On everywhere. A free feature on small tables, with new behaviour to test on 14 tables and some orders that should not be rearranged.
    • (c) On only where the order has no meaning (catalogue, exclusions, events). The most useful, and needs a decision per table.
    • other:

    Decision: (a), 2026-11-17. Sorting is off on embedded tables, with the sortable={false} prop the package added in 0.3.0 for this.

    OQ8: One pull request or several?

    • (a) ✅ recommended: one implementation plan and one pull request, the seven stages as phases. The standing practice; the intermediate states are not worth releasing, and the release path is proved before merge by the dry-run dispatch.
    • (b) Two: stage 1 (install and auth) first, labelled dont-release, then the rest. Proves CI and the image build on main before the large change depends on them, for one extra merge.
    • (c) One per stage. Smallest reviews, seven merges, and several releases of a half-migrated UI unless each is dont-release.
    • other:

    Decision: (a), 2026-11-17. One implementation plan, one pull request.

    OQ9: Which release does it cut?

    main is at 2.0.0.

    • (a) ✅ recommended: minor, which tags v2.1.0. The UI looks different and nothing breaks for an operator: no value, variable or API changes.
    • (b) patch, v2.0.1. Understates a visible change of frame.
    • (c) dont-release, shipping with the next feature release. Leaves main ahead of the last release by a large UI change.
    • other:

    Decision: (a), 2026-11-17. minor, which tags v2.1.0.
