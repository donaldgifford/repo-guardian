repo-guardian overview

repo-guardian: the overview and study guide

What this project is for, how the v2 system is built, where it bends and where it breaks. Written so that a reader with no prior exposure can explain any shipped part of it on a whiteboard.

Covers the v2 line (chart and binary 2.0.0-rc.4, DESIGN-0025 to 0027, IMPL-0025) as of 2026-10-04. Companion pages: controls redesign explainer and controls walkthrough (both proposed, not shipped). Everything on this page is built into the page: no network, no build step.

Start here

repo-guardian is a GitHub App that keeps every repository in an organisation compliant with a written policy: it discovers repositories, checks each one against rules, opens a pull request with the fix when something is missing, and reports the fleet's posture through an API and a UI. The code is Go, the control plane is Temporal, the state is Postgres, and it ships as one Helm chart.

The bar this page is written for: the Hashimoto Defense. The idea (from Mitchell Hashimoto, named here by the project owner) is that anyone who ships customer-facing work can be pulled aside at a moment's notice and explain any shipped system in it. Not line-level recall, not function names. The questions are: Why did you do X instead of Y? What happens if this actor behaves maliciously? What data structure did you use here and why? Where does this fail? Proofs of concept, demos, experiments and investigations are exempt; speed wins there. Shipped work is not. The defense drills at the end are the exam; the rest of the page is the course.

Part 1

The project: why it exists and what it refuses to be

The non-technical half. Who hurts without it, what it promises, what it deliberately does not do, the principles that keep recurring across thirty design documents, and how v1 became v2.

The problem

An organisation with hundreds to thousands of GitHub repositories cannot keep baseline configuration present and consistent by hand. CODEOWNERS files, Dependabot or Renovate configuration, the Backstage catalog-info.yaml, branch protection and repository settings drift, or are never created at all. Nobody notices until something downstream breaks: a security finding has no owner to route to, a vulnerable dependency sits unpatched because no updater was ever configured, an auditor asks for evidence that every production repository had code review enforced.

Security teams hurt first

Tools like Wiz route findings by repository owner. No ownership attribution means findings go unrouted. Ownership is the one property everything else hangs off.

Platform teams hurt second

They own the fleet but have no measured posture, only anecdotes. "How many repositories lack CODEOWNERS?" has no answer without a crawler.

Developers hurt third

Inconsistent or missing dependency-update config means slow patching and unreviewed changes. Every team reinvents the same five files.

Compliance owners hurt hardest

SOC 2 and ISO 27001 evidence gets reconstructed by hand at audit time. There is no history of when a repository became compliant or stopped being so.

Why existing tools did not fit

Who it is for

Eight stakeholders show up across the documents. Each wants a different surface, which is why v2 grew an API and a UI beside the operator's Grafana.

What it does, and what it refuses to do

repo-guardian is a Go GitHub App that reads one central HCL policy and evaluates it against every repository in every organisation where the App is installed. In v2 a Temporal control plane owns the schedule: one long-running workflow per repository re-checks every 24 hours with jitter, immediately on relevant webhooks, and fleet-wide after a policy change rolled out over a 24-hour window. Each check writes findings, one per rule with a status, a reason, a remediation and typed evidence, into Postgres with an append-only event log. It remediates by opening or updating a single PR per repository on a deterministic branch. A read-only OIDC-protected API, a business UI, a public status page and a markdown report read that state. Operators keep Grafana for the health of the service itself.

Goals

  • Every repository the App can see carries the files, settings and protection the policy declares, or has an open PR proposing them.
  • Ownership from Backstage reaches GitHub custom properties so security tooling can route by owner.
  • Compliance is a measured number per rule and per org with history, not an anecdote.
  • A platform team can run it with one policy file and one Helm release, and explain every PR it opens.
  • Leadership and compliance can read posture without Grafana; the public can read "is it working" without any detail.

Non-goals (each is a decision with a document behind it)

  • Not a blocking gate. Never a required status check; a repository can close the PR and nothing breaks. (RFC-0001)
  • Never commits to default branches, never merges its own PRs. Settings and branch-protection rules may opt into direct API writes; files never.
  • Not a code or secret scanner. It checks presence and shape of configuration, not content quality.
  • No in-repo overrides. One central policy; exemptions are reviewed ignore entries in git.
  • No write path from the UI or API, for the life of v2. No acknowledging, suppressing or re-running from a browser. (DESIGN-0027, INV-0018 Observation 8)
  • No notifications yet. Jira, Slack and webhook sinks are reserved as a future step.
  • GitHub only. GitLab and Forgejo were investigated, not built. Keys are provider-neutral so the door stays open.
  • One App credential across orgs. Per-org Apps are deferred until a structural trigger.
  • Not Temporal Cloud, and Temporal is not bundled. It is an operator prerequisite.
  • Not multi-tenant SaaS. One deployment per GitHub Enterprise Cloud estate.
  • v2 does not change what a check does. Rule semantics, PR behaviour and reconcilers are v1's, pinned by a parity suite.

Principles that keep recurring

Twelve ideas appear again and again, each born from a specific incident or decision. Knowing them lets you predict how the system behaves in a situation nobody wrote down.

The v1 to v2 story

By August 2026 v1 was one Deployment holding the webhook handler, a worker pool and the schedulers, with Postgres for state, a Valkey work queue (a list, two sorted sets, three Lua scripts and a reaper), SETNX leader election for four schedules, and a leader-only exporter publishing compliance as Prometheus gauges. It worked, and it had earned a dozen investigations. Three of them triggered v2.

INV-0009 · a status API and UI were wanted

Opened 2026-07-19. Options weighed: a subcommand or its own Deployment, OIDC, a read-only database role. Nothing shipped yet, but the shape was set.

INV-0018 · eleven observations

Opened 2026-09-23. Every replica held every secret. There was no business state to show: the engine knew why a repository failed and persisted only that it failed. Metrics were doing a database's job. Option D chosen: role split, findings store, platform UI. Observation 8 fixed the UI as read-only.

INV-0019 · Temporal as the control plane

Opened 2026-09-23. Each hand-built mechanism mapped to a Temporal primitive; Valkey dropped; the operating cost accepted. Three Approved designs followed on 2026-09-24, every open question resolved by 09-25.

Toggle between the two shapes. Dashed nodes were removed; purple nodes are new. The policy engine in the middle did not change, and that is the point: a parity suite of 100 golden files proves every GitHub write and every verdict is byte-identical before and after.

What v2 drops

  • The Valkey queue and its four keys, the in-process worker pool, the stale sweeper, SETNX leader election.
  • The posture exporter and roughly 25 business metrics.
  • The webhook handler living inside the worker.

What v2 keeps unchanged

  • The policy engine, every rule's semantics, the reconcilers, the HCL schema.
  • PR identity: branch name, title, sticky-comment marker. TestPRIdentity_IsFrozen pins the literals so v1 and v2 adopt each other's open PRs.

Migration posture

  • Roll-forward only. v1 posture is adopted once into findings with reason migrated_from_v1; v1 kept no per-rule history worth replaying.
  • migrate --dry-run rehearses in one rolled-back transaction; migrate verify-shadow classifies every v1/v2 pair and exits non-zero on anything unexplained.
  • Rollback is a worker version switch; v1 tables are never touched.
Release posture on the v2 line. The semver bump runs on main only. Release candidates v2.0.0-rc.N are tagged by hand from v2 behind dont-release PRs and published by dispatching the registry workflows with the tag; a tag with a dash never moves latest. Shipped: rc.1 on 2026-09-26 (#188), rc.2 through rc.4 on 2026-09-27 (#189 to #193). rc.5 is planned by IMPL-0026 and held until its live checks pass. At v2.0.0 the v2 branch fast-forwards main.

Constraints and environment

Clusters

Homelab Talos Kubernetes for dev and test, consumed through kustomize plus Helm in ArgoCD. EKS is the production target with RDS or Aurora Postgres. The ArgoCD path is why every chart template stamps namespace explicitly.

Fleet

Two GitHub organisations today, twenty or more planned, plus a few self-hosted GitLab instances someday. GitHub Enterprise Cloud only, including *.ghe.com data residency via GITHUB_HOST; GitHub Enterprise Server is out of scope.

External prerequisites for v2

Postgres 18 (baked, CloudNativePG or external), a Temporal server at 1.31 or newer (reference cluster in contrib/temporal/), an OIDC issuer when API or UI auth is on (Keycloak in the homelab), Prometheus and Grafana 13+ for operators.

Rate limits

5,000 calls per hour per installation (15,000 on Enterprise). Every call is attributed to an installation; webhook-triggered checks get half the reserve so human-triggered work goes first.

Tooling floors

Go 1.26, golangci-lint v2 with 50+ linters, mockery v3, helm 4.2, sqlc, bun 1.3, all pinned in mise.toml. Grafana 13+ with concrete datasource UIDs. GoReleaser binaries GPG-signed; images and charts cosign-signed with SLSA Level 3 provenance.

Documentation discipline

docz-managed docs/{rfc,design,impl,investigation,adr}. Design documents are planning-only. Cross-cutting designs get a code audit before the implementation plan. Open questions use a letter-keyed format with the recommendation first.

Open questions still open for v2

How work happens here

The repository has a documented path from idea to shipped code, and the path explains why the documents read the way they do.

Document types (docz)

  • INV: an investigation records observations and options; it ends with a recommendation, never a decision.
  • RFC: a high-level proposal. Two exist; RFC-0002 (the HCL policy engine) is Accepted, RFC-0001 was never promoted from Draft.
  • DESIGN: the technical design with a Decisions ledger and letter-keyed open questions, (a) being the recommendation. Planning-only: a design never carries code.
  • IMPL: the phased plan with checkboxes, acceptance criteria and quality gates; worked phase by phase, sometimes by an automated loop that checks boxes as it goes.
  • ADR: the type exists, the folder holds only its index. Decisions live in the designs and in the trade-offs table above.

Rules that shape the code

  • Never commit to main; every change is a branch and a PR with exactly one semver label (major, minor, patch, dont-release).
  • Release candidates and docs-only changes use dont-release; rc tags are pushed by hand.
  • Make targets for everything; the Makefile is the one entry point for lint, test, generate and drift gates.
  • Generated artefacts are committed and drift-gated: sqlc, oapi-codegen, dashboards, UI types, chart README. Hand edits turn CI red.
  • Tests must be non-vacuous: neutralise the fix, confirm the test fails, restore. Several incidents were tests that passed for the wrong reason.
  • CLAUDE.md is the working-notes file: engine subtleties, post-mortems and contracts a newcomer would otherwise learn by breaking something.

Roles and topology

One image, one binary; the first argument is the role. The chart renders one Deployment per role under topology: split (the default) or a single Deployment under all. What a pod can reach is decided by which secrets the chart mounts and by what config.LoadRole refuses, not by trust in the code. Toggle the topology.

App private keywebhook secretPostgres DSNread-only DSNTemporal credentialspolicy + templates

ingest refuses two things

LoadRole(RoleIngest) fails startup if the App private key or STORE_DSN is set, and the chart never mounts them. A leaked ingest pod can forge deliveries into Temporal; it cannot read a repository or a row. It does read the policy, only to compute the push-watched paths; a policy error fails startup rather than silently dropping every push.

api never dials Temporal

The api role gets no Temporal environment and dialTemporal returns no client for it, pinned by test. It reads through an 8-connection pool whose sessions are forced read-only with a 5-second statement timeout. In all it may fall back to the read-write DSN; the session settings still apply.

Readiness is cached

Checks run in the background every 10 seconds with a 5-second timeout; /readyz reads the cached verdict, so a probe storm never fans out to Temporal or Postgres. Workers add a schema check and, after a two-minute grace, a deployment check: a versioned worker that is not the current build gets no tasks and must not report ready.

Life of one check

What Engine.CheckRepo does to one repository, in the order the code does it, with GitHub call counts in brackets. This is the function v2 wraps in the CheckRepo activity and the function the parity suite freezes. Step through it; the diagram follows.

Typical costs

A compliant repository with two file rules, no PR and no reconcilers: about 5 to 7 calls. A first PR with two missing files: about 12. A steady-state sweep over an open PR where nothing changed: 8 to 12 reads and zero writes, pinned by TestConvergence_RenovateFirst_IdempotentReSweep_ZeroMutations.

Status is about the default branch

A file rule stays non_compliant while repo-guardian's own PR is open; remediation pr_open says what was done about it. Nothing that decides an action reads Reason or Evidence: enrichment is data-only, which is what let the parity goldens stay byte-identical.

Where it fails

Setting and branch-protection evaluation errors fail the whole check with a nil result (a partial set would let delete-not-in drop unvisited rows). Reconciler errors are logged and never abort. Throttles and skips surface as typed errors the activity classifies.

Check modes

The order of gates, per rule, per repository

Scope is checked before ignore; the two counters never both fire for one rule on one repository. The when-gate is content-only, default-branch-only and fail-closed: a referee error closes it. Everything here runs in the primary pass, which owns every counter; the reconciler pass re-applies the same gates silently, reusing the memoised gate result. Gate state lives on a per-check evaluator, never on the shared engine, because the engine is shared across worker goroutines.

Setting rules

Eight properties: vulnerability_alerts_enabled, default_branch, has_issues, has_wiki, delete_branch_on_merge, allow_merge_commit, allow_squash_merge, allow_rebase_merge. Mismatch with remediate = false records non_compliant/setting_mismatch with remediation disabled. With remediate = true the API write happens and the outcome is compliant with remediation applied, so self-healing never flaps.

Branch-protection rules

Rulesets API. A missing default branch is not_applicable/branch_missing, not a failure. Compared: a matching ruleset exists, required_approvals, dismiss_stale_reviews, require_linear_history. Caveat: enforce_admins and the contents of require_status_checks are written on remediation but never diffed; drift in either is invisible.

PR templates

Three scopes (defaults.pr, rule.pr, reconcile.pr) merged field by field: the child wins on every set field, unset fields inherit while inherits is true, labels = [] is an explicit override tracked by a sidecar flag because HCL cannot tell empty from absent. Multi-rule bundles render every title and fall back to the default on conflict; the body is always the default's. Bodies over 65,000 characters are truncated with a marker.

Templates

Renderer and contexts

  • Go text/template, one renderer per process, every body parsed once at startup with missingkey=error. Six embedded templates; a directory of .tmpl files overrides by name.
  • File templates see FileVars{Owner, Repo, DefaultBranch, Date, Rule, Catalog, Org}; PR templates see PRVars with the rule list and file list. .Catalog is nil for most rules: guard with {{ if .Catalog }}.
  • Helpers, no Sprig: env, default, join, lower, upper, title, propenv, yamlq. env reads any process variable, so templates are operator-trusted: never put secrets in PR text.
  • A literal ${{ ... }} for GitHub Actions must be written inside a backtick raw-string action; a bare one anywhere is a parse error.
  • --strict-templates renders every PR template against a zero context at startup to catch unknown fields.

Caveats found reading the code

  • skip_forks = false in HCL cannot turn off the default; the merge copies only true values. Only the SKIP_FORKS=false env var can.
  • Exact mode compares YAML by fmt.Sprintf("%v") of the unmarshalled values, so "1" versus 1 can produce a false mismatch.
  • Rules without a pr {} block never yield to a human's competing PR.
  • The reconciler pass re-reads file existence and content, so a rule with reconcilers pays its GETs twice per check.
  • The PR-convergence operations doc says orphans are kept when auto-close is off; the code gates orphan cleanup on orphan_cleanup, not auto_close_pr.

GitHub integration

REST only, through go-github v68; there is no GraphQL anywhere. One App JWT mints a token per installation, cached under a mutex. Every call goes through a chain of four transports whose order is pinned by a test. Click a layer.

Click a layer.

Three throttle shapes, one classifier

AsThrottled(err) matches our own refusal (*ThrottledError, raised when remaining ≤ limit × threshold), go-github's client-side pre-check (*RateLimitError, which fires above our transport when its header cache saw zero remaining and cannot be disabled in v68), and secondary limits (*AbuseRateLimitError). A bare type check on one shape silently misses the others; ratelimit_chain_test.go found this by failing.

Refuse, do not sleep

Under the reserve the transport returns an error instead of sending. The one surviving sleep is the reactive retry after a 403 with Retry-After, capped at 60 seconds; above the cap it fails fast as a throttle so the caller defers to the server's time. A static test keeps the cap below the old 5-minute ack timeout. In-handler sleeping is how INV-0012 Finding I happened: a reaper cloned a still-running job every interval while the transport slept for an hour.

Classification order matters

The activity checks AsThrottled before IsAccessDenied because a secondary rate limit is also a 403; the other order would park a healthy repository until the next discovery. Access denied covers 403 and 404 (GitHub answers "you may not see this" with 404).

Roughly how many calls does one check cost?

A model derived from the code walk above, not a measurement. Per-check call counts are logged (Usage.Calls()) but not exported as a metric.

Temporal: the control plane

Every repository is a long-running Temporal workflow with a timer and three signals. Checks are activities; budgets are a workflow per installation; discovery, snapshots and policy rollouts are schedules and service workflows. This replaced v1's hand-built queue, reaper, leader election and sweep.

Why Temporal, and what it cost

v1's control plane was a workflow engine written by hand on Valkey: a jobs list, an in-flight set, a delayed set, a reaper lock, three Lua scripts to keep "a job is in exactly one key", SETNX leader election for four schedules, a stale sweep over repo_state, and a best-effort write-back whose failures were counted but never retried. Once findings became the product (INV-0018), best-effort was not good enough. INV-0019 mapped each v1 mechanism to a Temporal primitive and compared three options.

What it buys

A repository is an entity with a timer, signals and durable side effects. One workflow per repo deletes the dedupe and sweep machinery. "Nothing blocks while holding a worker" becomes structural: a denied or deferred check holds a durable timer, not a slot. Priority and fairness come from the server.

What it costs

Four server services plus web and admintools, their own persistence and visibility stores, upgrades on Temporal's cadence. A determinism discipline for workflow code: GetVersion patches, replay tests, a workflow-task-failure alert. History growth needs ContinueAsNew. Version floor 1.31 (fairness GA, Update-with-Start GA).

Decisions

Self-hosted on Kubernetes, Valkey dropped, no pluggable backend, no Temporal Cloud. The chart ships no Temporal; contrib/temporal/ is a reference cluster on the upstream chart 1.7.0. Read:

Workflow catalogue

All on one task queue (TEMPORAL_TASK_QUEUE, default repo-guardian). Every start and activity carries a priority key and a fairness key equal to the installation id, so one noisy installation cannot starve the others. Payloads carry ids, counts and timestamps, never file content: evidence lives in Postgres under the check key. Click a workflow.

The RepoWorkflow loop, simulated

One execution per repository, ID repo/<repositories.id>. It waits on a timer or a signal, drains anything that arrived during a check so signals coalesce, acquires budget, runs the check activity, reports usage, records, and schedules the next check with ±10% jitter drawn through a SideEffect. Rate budget: one workflow per installation

GitHub rate limits are per installation, so the budget is one installation/<id> workflow holding BudgetState{Limit, Remaining, Reset, Reserved, Estimate, Leases}. A check acquires a lease through an Update (issued by the AcquireBudget activity, because workflow code cannot Update-with-Start) and reports what it spent through a Signal. The estimate is an EWMA of calls per check (weight 0.2, seeded at 20). Try the arithmetic.

Priority:

Grant rule

Grant iff Remaining − Reserved − reserve(p) ≥ ceil(Estimate), where reserve = ceil(Limit × threshold), halved for priority ≤ 2. That halving is the whole implementation of "human-triggered checks go first".

Unknown or denied

No report yet, or the reset time has passed: grant optimistically; the transport's reactive throttle is the backstop. Denied: WaitUntil = Reset + (NextLease mod 60)s, a deterministic spread that needs no SideEffect. A deferred check reports Remaining=0, closing the gate for every repo of that installation until reset.

Leases and handoff

Lease TTL is 20 minutes (the 15-minute check timeout plus 5), swept on every acquire, so a crashed check cannot leak budget. ContinueAsNew after 2,000 handled or on the server's suggestion; under load some completions come back UNHANDLED_COMMAND, which is a normal handoff: the Update errors back to the activity, which retries.

Determinism, versioning and the traps already hit

Workflow code does no I/O, by lint

A depguard rule on internal/workflows/*.go denies importing checker, store, github, reconciler or activities. Workflows reach activities by name constants only; payload types live in types.go. The glob is *.go because /** did not match.

Randomness goes through SideEffect

Interval jitter and the rollout's random point are recorded in history. The budget's wait spread is NextLease mod 60, deterministic by construction, so it needs none.

Replay is a CI gate

TestReplay_CapturedHistories replays every captured history and fails if the directory is empty. Any change to command order needs workflow.GetVersion. Only two histories exist today; homelab captures are deferred.

The marker trap

Phase 10 recorded budget-v1=1 with a no-op branch, so Phase 10 histories cannot replay on Phase 11+. Rule: never ship a GetVersion(..., 1) whose v1 branch is a placeholder. No Phase 10 build was ever deployed.

Versioned workers get no tasks until current

Deployment versioning is on (deployment repo-guardian, build ID from the image tag or VCS revision, AutoUpgrade). rc.1 workers sat idle because nobody promoted the build. Fix: PromoteBuild self-promotes newest-by-semver with a conflict-token CAS, and a deployment readiness check fails after 2 minutes if the pod is still not current, so idling is never silent.

The version check that crash-looped

CheckServerVersion (floor 1.31.0) uses GetSystemInfo, not GetClusterInfo: under a JWT authorizer the latter is cluster-scoped and rc.2 died on "Request unauthorized". Two auth modes ship: mTLS files, and OIDC client-credentials sent as a bearer token.

Where the control plane fails

Abuse, briefly. A forged webhook dies at HMAC (401) and never reaches Temporal. A replayed delivery is deduped on X-GitHub-Delivery. A repository that pushes constantly costs one short workflow per delivery (7-day history retention) and at most one follow-up check per in-flight check, and can only dip into half of its own installation's reserve. An installation that exhausts its budget sleeps until reset while the fairness key keeps it from starving others. Anyone with namespace write on Temporal can signal park or recheck; OSS Temporal has no finer authorization, so the boundary is mTLS plus network policy, which DESIGN-0028 hardens.

What persists where

  • Postgres: everything above, plus the untouched v1 tables (repo_state, rule_state, compliance_snapshot, schema_migrations) kept so v1 can be rolled back to.
  • Temporal: workflow histories and timers (7-day retention in the reference namespace), the budget state inside installation/<id>, schedules.
  • GitHub: the reconcile branch, the PR and its sticky comment are state too: the engine reads them back every check.
  • In-process only: installation tokens, the 30-minute org-schema cache, the Temporal OIDC token, the status page's atomic pointer, the OIDC key set.
  • Not present: Valkey or Redis (go-redis remains in go.mod only because the v1 deletion is deferred), object storage, an external cache.

The one write that matters: RecordCheck

Everything a check learned lands in one transaction, idempotent on the check key. Step through it.

Park: nil-vs-empty as a bool

Park(repoID, reason, clearFindings) sets active = false with a reason and writes a parked event. access_denied and removed keep findings: we learned nothing about the rules, and clearing would make an unreadable repository look compliant. archived and fork clear them with removed events: we read the repository and know no rule applies, and a parked repository is never re-checked to correct stale rows. Both directions are silently wrong if swapped.

Discovery is the only un-parker

UpsertDiscovered matches the row (by provider_repo_id first, then case-insensitive name), inserts or refreshes identity, and calls ReactivateRepository, documented in the SQL as the only statement that sets active = true. RecordCheck never touches active, pinned by test. This is INV-0015's subset invariant made structural.

Identity survives renames

An id match under a new org writes transferred; under a new name, renamed; a case-only change updates the row with no event. A name held by a different id is ErrIdentityConflict: a reused name is an operator decision, never a guess. GITHUB_HOST keys every record that names no host.

Conventions

  • RFC 9457 Problem bodies; only typed HTTP errors reach clients, anything else is logged and 500'd.
  • Lists default to 50, max 200; the store fetches limit+1 and returns Page{Items, More}.
  • Cursors are unsigned base64url {sort key, filter hash}; a cursor reused with other filters is 400. Unsigned is safe because every page re-applies the SQL scope: tampering can reorder, never widen.
  • pr_stale is computed in SQL from the evidence's PR created_at; the summary uses the same strict comparison.

Authentication: classify first, then verify

A bearer JWT from the OIDC issuer. The token is classified from its unverified header and claims first, in a fixed order, so every refusal carries a precise api_auth_failures_total{reason}; only then is the signature verified. go-oidc's own expiry check has no clock skew and its not-before leeway is five minutes, so expiry is checked by hand with a 60-second skew and the library runs with SkipExpiryCheck.

Authorization is coarse by design

API_AUTHZ_CONFIG is YAML: groups (group → orgs), defaultOrgs, clients (azp → groups for machine callers), strictly decoded, read at startup; the chart rolls pods on its checksum. The caller's scope is the union of mapped groups; * means all orgs; no match falls to defaultOrgs. An invisible org answers 404, identical to an unknown id, so existence does not leak across groups.

The zero-value trap

store.APIScope{} sees nothing; store.Scope{} (used by the report) sees everything. API callers default-deny, internal tools default-all. The shared compliance query takes a Scope, so complianceScope must check Empty() first or an empty API scope would read the whole fleet. TestAPIQueries_AreScoped fails any api_*.sql file missing the predicate (@scope_all OR lower(org) = ANY(@scope_orgs)).

Readiness and the issuer

Discovery runs in the background with backoff; until it succeeds every request is 503 unavailable and the oidc readiness check is false. The API never fails open. API_AUTH_ENABLED=false is the one foot-gun: a loud warning, principal anonymous with every org; the chart refuses to render a UI Ingress in that state.

The status page

StatusPage.Run refreshes every 30 seconds from one read-only transaction (last-hour checks and errors, service runs, rate snapshots, unscoped compliance) plus a Temporal backlog probe only when a client exists (the all role). Requests read an atomic pointer: zero queries per request, pinned by a test that serves 50 requests off one read. Before the first refresh the page is unknown; a failed refresh keeps the previous page and lets updated_at age. Compliance reads unmeasured without findings, never 100%. TestStatus_PrivacyGuard walks the Status schema and fails on any string field outside the enum allowlist, so nobody can add a free-text field that leaks a name.

Headers that bit

CSP default-src 'self'; script-src 'self'; frame-ancestors 'none', nosniff, and Referrer-Policy: same-origin, not no-referrer: under no-referrer Chrome sends Origin: null on a same-origin form POST, so the logout Origin check refused every sign-out. CI, release and the post-mortems

One CI workflow with a paths filter; every job declares needs: changes and an if: gate, so a docs-only change skips everything but the labeler while branch protection still sees the required checks satisfied. Five drift gates keep generated artefacts honest.

Standing workflows

  • security.yml: govulncheck to code scanning, per PR and weekly.
  • license-check.yml: an allowlist of licenses over the Go module graph.
  • pr-labels.yml: exactly one of major, minor, patch, dont-release to merge.
  • changelog-update.yml: git-cliff on release tags, skipping pre-releases.
  • gh-pages.yml: the mkdocs site, main only.

Linting as architecture

  • golangci-lint v2 with 50+ linters: cyclomatic ≤ 15, cognitive ≤ 30, function length ≤ 100, nesting ≤ 4, lines ≤ 150.
  • depguard rules carry two design boundaries: workflow code may not import anything that does I/O; API code may not import the GitHub client, the postgres package or pgx.
  • The depguard file glob is **/internal/workflows/*.go; /** did not match, which is the kind of detail that silently disables a boundary.

The gate that does not exist

Regenerated mockery mocks are not diffed in CI. A stale mock will not fail a PR; regenerate by hand with make mocks after touching an interface. Everything else generated is gated.

  • TemporalWorkerSlotsExhausted uses max by: it fires only when no pod has a slot.
  • Per-alert for, severity, threshold and enabled overrides; enabled: false works only since rc.2 because sprig's default swallowed false.

The real ceiling is GitHub

Throughput is bound by the rate budget per installation, not by workers: "raising concurrency or replicas past the budget only adds waiting". Everything else is designed to spend that budget fairly: the EWMA cost estimate, leases, the half reserve for human-triggered checks, the installation fairness key on every task, and per-repo jitter so neither the schedule nor a rollout stampedes. What costs calls: candidate paths (one GET each, no tree fetch), the reconciler pass re-reading, orphan probes per non-actionable rule.

Not measured, not present

  • No pprof endpoint anywhere; no profiling data in the tree.
  • No AI or LLM component, so no evals or judge models; the project is deterministic code throughout.
  • Not load-tested: the homelab 20,000-pair burst, a patched deploy over running executions, 20,000 open executions on SQL visibility, KEDA under any auth, ingest throughput, the UI.
  • Not exported as metrics: per-check call counts (logged only), template render time, per-rule latency, reconciler durations.
  • Only two captured workflow histories back the replay gate; homelab captures are deferred.

Testing

Fakes, not expectation plumbing

mockery v3 generates mocks for Store, Queue, Scheduler and the GitHub client. Tests for the client do not drive expectations: the checker, scheduler and reconciler packages keep hand-written stateful fakes (seed a map, the fake computes the answer) that embed the generated mock, so an interface addition is absorbed by regeneration. An un-overridden method panics with "no return value specified", on purpose: a silent zero value is how a skip-on-match assertion once passed vacuously because the fake's list method always returned nil.

Conventions

  • t.Parallel() and t.Setenv() panic together; config tests avoid parallel.
  • Counter assertions via testutil.ToFloat64; Reset() between tests.
  • Per-file recorders (recordingQueue, fakeStore) when a test only needs to observe a call; never a new in-process backend.
  • Neutralise the fix, confirm the test fails, restore: the rule that keeps goldens and guards honest.
  • Integration tests run as a non-superuser Postgres role so the append-only grant actually binds.

Known gaps

  • No CI diff of regenerated mocks.
  • Two replay histories; the integration harness recaptures them.
  • UI e2e runs locally (13 Playwright cases green); the CI job first runs on push, deferred.
  • Coverage target 60%, threshold 40%, via Codecov; no codecov.yaml in the tree despite references.
