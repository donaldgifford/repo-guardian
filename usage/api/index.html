    The read-only API

    repo-guardian v2 serves a read-only JSON API over the findings store (DESIGN-0027). It backs the business UI and the public status page, and anything else that wants compliance data: a dashboard, a CI gate, a report. Every endpoint is a GET.

    The contract is api/openapi.yaml. The running API serves it at /api/v1/openapi.yaml without a token, and every release attaches it as openapi.yaml.

    Enabling it

    api:
  enabled: true
  auth:
    issuer: https://idp.example.com
    audience: repo-guardian-api
  authz:
    groups:
      platform-engineering: ["*"]
      team-web: ["acme"]

    In topology split this renders an api Deployment (two replicas and a PDB) and a ClusterIP Service, <release>-repo-guardian-api. In all the API runs inside the one Deployment on api.port and the same Service targets it. The Service is never published by the chart: people reach the API through the UI, and machines from inside the cluster or through an ingress you own.

    The API reads Postgres through a read-only role. See the chart README, "The API's read-only role", for how each Postgres mode provides it.

    Authentication

    Every endpoint except /status and /openapi.yaml needs Authorization: Bearer <access token>, an OIDC access token issued for the API's audience. The API:

    • discovers the issuer (api.auth.issuer) and verifies the signature against its JWKS (RS256 or ES256 only);
    • requires iss to equal the issuer exactly and aud to contain api.auth.audience;
    • allows 60 seconds of clock skew on exp and nbf;
    • refuses ID tokens: anything carrying a nonce or at_hash, or a typ claim of ID;
    • reads the caller's name from api.auth.nameClaim (default preferred_username), groups from api.auth.groupsClaim (default groups) and a machine client from api.auth.clientClaim (default azp), each a top-level claim.

    Until discovery succeeds the API answers 503 and is not ready. Refusals are counted in repo_guardian_api_auth_failures_total{reason}.

    api.auth.enabled: false turns authentication off for a pod-network-only API. The chart then refuses to render the UI or its Ingress (INV-0009).

    Setting up a provider, with recipes for the common ones and a checklist for the rest, is in Identity providers.

    Authorization

    api.authz maps groups to the orgs they may see. It is rendered into a ConfigMap, read at startup, and a checksum annotation rolls the API pods when it changes.

    api:
  authz:
    groups:
      platform-engineering: ["*"]      # every org
      team-web: ["acme", "acme-labs"]
    defaultOrgs: []                     # for callers matching no group
    clients:
      ci-dashboard: [platform-engineering]
    • A caller sees the union of its groups' orgs. "*" is every org.
    • defaultOrgs applies only when none of the caller's groups is mapped. Leave it empty so an unmapped user sees nothing.
    • clients maps a machine client, by the claim api.auth.clientClaim names, to groups defined above. It is for IdPs that put no groups on client-credentials tokens. Never map the UI's client ID here. Every user token from the UI carries repo-guardian-ui in that claim, so mapping it would grant every signed-in user those groups.
    • Scoping is applied in SQL on every query, including every page of a list. An org the caller cannot see answers 404, the same as one that does not exist. A caller who can see no org gets 403 everywhere except /me, and the UI turns that into an "ask for access" page.

    Endpoints

    All live under /api/v1. The OpenAPI document has the full schemas.

    Endpoint Returns
    /status public service status (below)
    /me the caller, and the orgs it may see
    /summary tracked and parked repositories (and parked by reason), the fleet posture, how many controls have a failing result, open PRs, the remediation backlog (reserved, open, recommended or failed), repositories evaluated in the last 24 hours, the active policy version and finding_age: non-compliant results by time since they last changed, in six buckets (<1d, 1-7d, 7-30d, 30-90d, 90-180d, 180d+) that sum to the posture's non_compliant, and open_prs_by_age (<1d, 1-7d, 7-30d, 30d+ by when each was opened) summing to open_prs
    /controls, /controls/{id} each assigned control's posture (?org= narrows it); one control by org and lineage, with the versions and revisions each org carries
    /orgs, /orgs/{org} posture and open_prs per org; one org's baseline against what it added (percent and coverage each), its controls, its five worst and its exclusions
    /repositories, /repositories/{id} repositories filtered by org, active, park_reason, policy_state, q, each with the posture over its own assignments (compliance); one repository with its last evaluation, policy state and whether each App can reach it
    /repositories/{id}/controls the repository's assignments in remediation order, each with its bucket, mode, rule results, evidence and latest remediation
    /repositories/{id}/evaluations, /repositories/{id}/events the evaluation log; result changes, repository events and remediation events
    /results recorded control results across repositories by bucket, control, rule (failing or erroring), org and decision, sorted by last change (since_asc, since_desc) or by open pull request age (pr_age, oldest first, results with none last), each with its failing rules, reason and latest remediation (kind, state, pull request number and URL, age_days); pr_stale=true keeps results whose open pull request is at least 30 days old, false the rest; total on the first page. A finding is a result in the non_compliant bucket, so ?bucket=non_compliant's total is the summary's count
    /remediations remediations newest first, by kind, state, org, control, hold (repeatable) and older_than_days, each with its proposal and step journal; a branch hold also lists the results held before a pull request exists (below)
    /remediations/activity pull request throughput: repo-guardian pull requests opened and closed on each UTC day of the last days (1–90, default 14), today included, every day present
    POST /repositories/{id}/evaluate asks for an evaluation now (below)
    /compliance/history each UTC day's last snapshot per org, control and lineage, by control, org and days (1–365, default 30); aggregate=fleet, org or control sums each day's rows to one point per day (per org, per control) with the percentages recomputed from the sums
    /policies the active policy as the caller may see it: its version and rollout, each visible org's layer, the catalogue entries those reference, and the enterprise layer for callers who see every org
    /openapi.yaml the contract (public)

    Posture. Every compliance object is a Posture: one count per bucket (compliant, non-compliant, pending, stale, three unmeasurable reasons, not applicable, unknown, excluded), assigned, and two percentages floored to one decimal. percent is compliant / (compliant + non_compliant); coverage is the measured assignments (compliant, non-compliant, not applicable) over assigned. When the denominator is zero the value is null, never 100, and the UI prints "no data". The API sums rows and recomputes both from the sums, exactly as the SQL does, so no total is an average of percentages.

    Evidence explains a rule result. Each object carries evidence_kind (<control type>.<rule kind>) and evidence_version; framework evidence, written when an evaluation could not decide, adds reason. Values in it came from repositories (paths, file contents, setting values): treat them as data and never render them as markup.

    Remediations. /remediations lists one row per remediation: a pull request (reserved through merged or a close), a recommendation, or a direct apply with its proposal (each resource's value before and the value asked for) and steps journal. Open pull requests older than N days are ?kind=pull_request&state=open&older_than_days=N, outstanding recommendations ?state=recommended, blocked cleanup ?hold=permission. The branch holds (pr_cap, foreign_branch, stale_branch, conflict) are set on a result before any pull request exists, so ?hold= with one of them also lists those results as rows of their own: kind pull_request, no id, state or pull request, and created_at when the hold began. One cursor pages both kinds of row.

    Re-evaluation. POST /repositories/{id}/evaluate signals the repository's evaluation workflow at the highest priority and answers 202. It is the API's only write and touches no table. Visibility comes first (404, as for the GET). An API replica with no Temporal client answers 501, and the UI hides its button; set api.temporal in the chart to give the api role one. A parked repository is 409 with type parked, and one with no running workflow 409 workflow_missing. Each replica sends at most one signal per repository per minute and answers 202 to the rest.

    curl -s -H "Authorization: Bearer $TOKEN" \
  "https://guardian.example.com/api/v1/controls?org=acme"

    The status page

    GET /api/v1/status is public when api.status.public is true (the default). It reports an overall state, one state per component (checks, webhooks, discovery, snapshots, and backlog_evaluation / backlog_remediation for each queue whose App is configured) with a fixed-template detail such as "last success 3m ago", the deployment's topology (split or all), and apps: each App with an installation and its installation, suspended and reachable-repository counts. compliance carries the fleet percent and coverage and compliance.history: one point per UTC day over the last 30 days, taken from that day's last snapshot. operations adds repositories evaluated in the last 24 hours, remediation_backlog (outstanding remediations, as on /summary), overdue (managed repositories with no successful evaluation within twice EVAL_INTERVAL), tracked repositories, the newest policy version's rollout_state (none, in_progress or complete, with rollout_completed_at) and last_snapshot_at. It names no org, repository, control or installation and carries no error text. The API computes it every 30 seconds in memory, so a request never reaches the database.

    Pagination

    Lists return items and, when there is more, next_cursor. Pass it back unchanged as ?cursor=, with the same filters, to get the next page. limit defaults to 50 and is capped at 200.

    Cursors are keyset positions, not offsets, so pages stay stable while checks write. A cursor is bound to the filters it was issued with: sending it with different filters is a 400. Cursors are opaque and unsigned. Tampering with one cannot widen what you see, because scoping is applied to every page.

    Errors

    Errors are RFC 9457 application/problem+json:

    {"type": "about:blank", "title": "Not Found", "status": 404, "detail": "no such org", "request_id": "c0ffee…"}
    Status When
    400 a malformed filter, limit or cursor, or a cursor from other filters
    401 no token, or a token that fails verification; carries WWW-Authenticate: Bearer
    403 the caller can see no org
    404 no such resource, or one in an org the caller cannot see
    503 the issuer has not been discovered yet

    request_id matches the API's logs. Quote it when reporting a problem.

    Compatibility

    /api/v1 changes only additively:

    • new endpoints, new optional query parameters and new response fields may appear;
    • enums documented as open (status, reason, remediation, park reason, trigger, component) may gain values, so treat an unknown value as opaque rather than failing;
    • nothing is removed or renamed, and no field changes type.

    The contract's info.version follows semver: an addition bumps the minor version. 2.0.0 is the controls line (IMPL-0029): the findings endpoints (/rules, /findings, /policy, /installations, /repositories/{id}/checks) are gone, replaced by /controls, /policies, /repositories/{id}/controls and /repositories/{id}/evaluations, and every compliance object is a Posture. It ships before v2.0.0 is released, so no 1.x client exists to break.

    2.1.0 (IMPL-0030) adds remediation: /remediations, /remediations/activity and /results; aggregate on /compliance/history; compliance on every repository; each assignment's latest remediation on /repositories/{id}/controls; remediation events in the timeline; and on /summary remediation_backlog, parked_by_reason, controls_failing, finding_age and open_prs_by_age (the status page gains remediation_backlog). On a rule-level event (rule_id set), from_status and to_status are rule statuses (pass, fail, error, unknown, not applicable), not result statuses.

    Anything else would be /api/v2, served beside v1 for a deprecation window. The UI and the API are released together from one tag, so the UI always matches its API.
